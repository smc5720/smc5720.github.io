## 개요

에이전트 데모는 대개 순조롭게 흘러갑니다. 모델이 도구를 고르고, 도구가 200을 돌려주면 다음 단계로 넘어갑니다. 운영 환경은 다릅니다. 도구 호출이 아무 응답 없이 끝나는 경우가 생깁니다.

Dimitris Kyrkos는 바로 이 지점에서 올바른 판단이 잘못된 결과로 바뀐다고 지적합니다. 모델이 추론을 완벽하게 해냈더라도, 실패가 추론이 끝난 *뒤에* 일어나면 프롬프트를 고치거나 더 큰 모델로 바꿔도 해결되지 않습니다. 저자는 에이전트의 도구 호출을 "LLM이 어떤 프로시저를 부를지 고르는 원격 프로시저 호출(RPC)"로 다시 봐야 한다고 주장합니다.

## 본문

### 환불이 두 번 나가는 과정

저자가 든 예시는 실제 사고가 아니라 설명용 시나리오입니다. 다만 아주 흔하게 벌어질 수 있는 일입니다.

1. 에이전트가 고객 지원 티켓을 처리하다가 환불이 필요하다고 판단하고 `POST /refunds`를 호출합니다.
2. 결제 서비스는 환불을 처리해 원장에 기록한 뒤 응답을 보내기 시작합니다.
3. 그 순간 네트워크가 잠깐 끊깁니다. 에이전트 쪽 HTTP 클라이언트는 타임아웃 에러를 냅니다.
4. 에이전트 입장에서는 호출이 실패했고, 결제 서비스 입장에서는 성공했습니다. 에이전트 루프는 에러를 보고 가장 자연스러운 선택, 즉 재시도를 합니다.

결과적으로 고객은 환불을 두 번 받습니다. 모델은 올바른 동작을 올바른 인자로 골랐지만 결과는 틀렸습니다.

### 다섯 가지 실패 패턴

저자는 이 사고를 다섯 가지 설계 결함으로 나눠 설명합니다.

**1. 타임아웃을 '실패'로 읽는다**

타임아웃이 알려주는 건 "응답을 못 받았다"는 사실 하나뿐입니다. 작업이 일어나지 않았다는 뜻은 아닙니다. 그런데 도구 에러를 "도구 실패, 다음 행동을 결정하라"로 감싸는 에이전트 프레임워크는 서로 다른 세 상황을 하나로 뭉갭니다.

- 요청이 서비스에 닿지도 못한 경우
- 요청이 닿았지만 거절된 경우
- 요청이 닿아 성공했는데 응답만 사라진 경우

이 중 무작정 재시도해도 안전한 건 앞의 두 경우뿐입니다.

**2. 멱등성 키가 없다**

에이전트가 멱등성 키(idempotency key)를 보냈다면 두 번째 환불 호출은 아무 일도 하지 않고 첫 결과를 그대로 돌려줬을 겁니다. 핵심은 키를 애플리케이션이 첫 시도 *전에* 만들고, 같은 의도의 재시도마다 똑같은 키를 재사용해야 한다는 점입니다.

```python
intent = actions.record_intent(
    kind="refund",
    order_id=order.id,
    amount=amount,
    idempotency_key=uuid4(),   # created once, stored with the intent
)

try:
    result = payments.refund(
        order_id=order.id,
        amount=amount,
        idempotency_key=intent.idempotency_key,
    )
    actions.mark_confirmed(intent.id, result)
except Timeout:
    actions.mark_unknown(intent.id)   # NOT "failed"
```

저자는 키를 어디에 두느냐가 중요하다고 강조합니다. 모델이 키를 만들거나, 시도할 때마다 새로 만든다면 아무것도 막지 못합니다.

**3. 상태가 컨텍스트 윈도우에만 있다**

"주문 4812번 환불을 이미 시도했다"는 기록이 대화 기록에만 남아 있으면 프로세스 크래시, 컨텍스트 잘림, 워커 재시작 한 번에 사라집니다. 실행 전에 의도를 영속 저장소에 먼저 써 둬야 다음에 작업을 이어받는 프로세스가 그 기록을 볼 수 있습니다.

**4. '결과 불명' 상태가 없다**

대부분의 액션 모델에는 종료 상태가 성공과 실패 두 가지뿐입니다. 저자는 신뢰할 수 있는 시스템이라면 최소한 다음 네 가지가 필요하다고 봅니다.

- `submitted`: 요청은 보냈고 아직 응답이 없음
- `confirmed`: 하위 시스템이 처리를 확인함
- `failed`: 하위 시스템이 명시적으로 거절함
- `unknown`: 어떻게 됐는지 알 수 없음

이 가운데 중요한 건 `unknown`입니다. 이 상태가 자동 재시도를 막고, 대신 정합성 확인(reconciliation)을 시작하게 해야 합니다.

**5. 정합성 확인 경로가 없다**

액션이 `unknown`에 들어가면 누군가는 실제로 무슨 일이 있었는지 확인해야 합니다. 멱등성 키나 주문 ID로 결제 서비스를 조회하고, 원장과 맞춰 본 뒤 의도를 `confirmed`나 `failed`로 옮기는 식입니다. 백그라운드 작업이든, 주기적 점검이든, 고액 건이라면 사람이 처리하는 대기열이든 상관없습니다. 다만 에이전트가 혼자 "아마 됐겠지" 혹은 "아마 실패했겠지" 하고 결론 내리는 방식이어서는 안 된다는 게 저자의 입장입니다.

### 관점 바꾸기: 모델은 제안하고, 애플리케이션은 실행 상태를 가진다

저자의 결론은 간단합니다. 에이전트의 도구 사용은 결국 불안정한 네트워크 위의 RPC이고, 우리가 이미 알고 있는 원칙이 그대로 적용됩니다. 멱등성, 영속적인 의도 로그, 불확실성을 명시하는 상태, 그리고 정합성 확인입니다.

역할은 이렇게 나눕니다.

- **모델은** 어떤 액션을 할지 *제안*한다.
- **애플리케이션은** 실행 상태를 *소유*한다. 키, 의도 기록, 상태값, 재시도 정책이 모두 여기에 속한다.

읽기 작업이라면 "다시 시도"를 기본값으로 둬도 괜찮습니다. 하지만 상태를 바꾸는 작업이라면 첫 시도가 반영되지 않았다는 사실을 확인했거나, 하위 시스템이 재시도해도 중복 적용되지 않는다고 보장할 때만 안전합니다.

### 새로 만들 것인가, 기존 체계에 붙일 것인가

이미 멱등성 키와 아웃박스·원장 패턴으로 결제나 주문 흐름을 운영하고 있다면, 에이전트가 API를 직접 부르게 두지 말고 기존 체계를 거치도록 연결하면 대부분 해결됩니다. 그런 체계가 없다면 돈이나 데이터를 움직이는 작업에 에이전트 쓰기 권한을 주기 전에 그것부터 만들거나 도입해야 한다고 저자는 말합니다.

글 말미에서 저자는 독자에게 묻습니다. 에이전트 워크플로에서 "실행됐는지 모르는" 경우를 어떻게 다루고 있는가. 재시도를 막는지, 정합성을 확인하는지, 아니면 사람에게 넘기는지.
