## 개요

OpenAI Codex CLI의 로컬 로그 데이터베이스 `~/.codex/logs_2.sqlite`가 SSD에 엄청난 양의 데이터를 쓰고 있었다는 보고가 나왔습니다. 한 개발자의 PC에서는 **21일 동안 약 37TB**가 기록됐습니다. 하루 평균 약 1.7TB이고, 같은 속도로 1년을 쓰면 약 640TB입니다.

그런데 로그 파일 자체는 작았습니다. Finder, 탐색기, `du` 같은 일반적인 용량 확인 도구로는 아무 이상도 보이지 않았습니다. 새 로그를 넣는 만큼 오래된 로그를 지웠기 때문에, 파일 크기는 일정했지만 디스크는 쉬지 않고 쓰기 작업을 하고 있었습니다.

원인으로는 기본값으로 켜진 TRACE 레벨 로깅이 지목됐습니다. 원문이 인용한 조사에 따르면 **0.142.0** 버전에서 로그 쓰기가 초기 테스트 기준 약 **85%** 줄었습니다. 예전 버전을 오래 썼다면 먼저 업데이트하고, 실제 쓰기량과 SSD 누적 쓰기 카운터를 확인해 보는 게 좋습니다.

## 숫자부터 보면

| 항목 | 값 |
| --- | --- |
| 보고된 쓰기량 | 약 37TB |
| 측정 기간 | 21일 |
| 하루 평균 | 약 1.7TB |
| 1년 환산 | 약 640TB |

이 수치는 모든 Codex 사용자에게 똑같이 적용되는 값이 아닙니다. 장시간 계속 돌린 한 대의 머신에서 나온 데이터입니다. 1년 환산치도 매일 같은 작업량이 이어진다고 가정한 단순 계산입니다. 짧게 쓰는 사람은 훨씬 적게 쓰고, 도구를 계속 켜 두거나 자동화에 쓰는 사람은 예상보다 훨씬 많이 쓸 수 있습니다.

저자가 강조하는 점은 "모든 SSD가 1년 만에 망가진다"가 아니라, 이 정도 쓰기량이면 사용자가 알아차리고 관리해야 할 수준이라는 것입니다.

## 파일 크기로는 왜 알 수 없었나

보통 디스크 문제를 의심하면 이렇게 확인합니다.

```bash
du -sh ~/.codex
ls -lh ~/.codex/logs_2.sqlite*
```

이 명령이 알려주는 건 "지금 데이터가 얼마나 저장돼 있는가"입니다. "지금까지 얼마나 많이 썼는가"는 알려주지 않습니다.

Codex 로그 DB는 진단 정보를 일정량만 보관하도록 설계됐습니다. 새 행을 넣고 오래된 행을 지우니 크기는 그대로였습니다. 폴더는 조용해 보였지만 디스크는 계속 일하고 있었던 셈입니다.

원문은 이를 테이블이 네 개뿐인 카페에 비유합니다. 정오에 창밖에서 봐도 손님 네 명, 저녁 6시에 봐도 네 명입니다. 테이블 수만 봐서는 그 사이에 손님이 8명 왔는지 800명 왔는지 알 수 없습니다.

## 무엇이 그렇게 많이 썼나

보고된 이슈는 기본값이 **TRACE**로 설정된 로깅 경로를 원인으로 짚습니다. TRACE는 Rust tracing 생태계에서 가장 상세한 로그 레벨입니다. 특정 장애를 깊게 파고들 때는 유용하지만, 평소에는 너무 시끄러운 정보까지 담습니다.

- 파일 열기 이벤트
- 네트워크·WebSocket 원시 데이터
- 전송 계층 세부 정보
- 텔레메트리 관련 처리
- 의존 라이브러리 로그를 애플리케이션 tracing으로 넘긴 메시지

원문이 인용한 분석에 따르면 보관된 로그 본문 크기의 **70.7%**가 TRACE 레벨 항목이었습니다. 양이 가장 많았던 대상은 WebSocket 처리, OpenTelemetry 관련 로그, 의존성 로그 브리지, 클라이언트 전송 코드였습니다.

## 세 가지 문제가 겹쳤다

하나씩 떼어 보면 꼭 나쁜 설계라고 하기는 어렵습니다. 문제는 셋이 한꺼번에 겹쳤다는 데 있습니다.

### 1. TRACE가 기본으로 켜져 있었다

TRACE는 디버깅할 때 직접 켜는 레벨이지, 몇 시간씩 쓰는 도구의 기본값으로 둘 레벨이 아닙니다. 보고에 따르면 Codex는 피드백용 로깅 싱크를 TRACE 레벨로 초기화했습니다. 그러다 보니 평범한 작업 하나하나가 대량의 진단 데이터로 바뀌었습니다.

### 2. `RUST_LOG=warn`이 제대로 먹히지 않았다

Rust 개발자라면 로그를 줄이려고 가장 먼저 이렇게 실행합니다.

```bash
RUST_LOG=warn codex
```

이슈 분석에 따르면 이 설정이 해당 싱크에는 온전히 적용되지 않았습니다. 대상별로 따로 지정하지 않은 경우 Codex 내부 기본값이 그대로 남아 시끄러운 로그를 계속 허용했습니다.

설정이 아예 없는 것보다 더 곤란한 상황입니다. 사용자는 로그를 줄였다고 믿는데, 디스크에는 여전히 같은 양의 쓰기가 들어가기 때문입니다.

### 3. SQLite가 로그를 저장소 부하로 바꿨다

작고 구조화된 로컬 데이터를 다루기에 SQLite는 좋은 선택입니다. 하지만 TRACE 이벤트가 끊임없이 들어오고, 삽입·삭제·인덱스 갱신·체크포인트가 반복되면 DB 크기가 작아도 쓰기량은 크게 늘어납니다.

원문은 "SQLite가 나쁘다"는 얘기가 아니라고 선을 긋습니다. 계속 켜 두면 안 되는 로그 레벨을, 쓰기 부하가 큰 보관 루프에 연결한 것이 문제였다는 설명입니다.

## 운영체제가 보여주지 않는 쓰기 증폭

이번 사례에는 두 단계의 증폭이 있습니다.

### SQLite 단계

SQLite는 보통 WAL(write-ahead logging) 모드를 씁니다. 단순하게 정리하면 이런 흐름입니다.

```text
1. 로그 이벤트가 WAL 파일에 추가된다.
2. SQLite가 나중에 체크포인트로 본 DB에 반영한다.
3. 보관량을 유지하려고 오래된 행을 삭제한다.
4. 그 과정에서 인덱스와 DB 페이지가 갱신된다.
```

로그 이벤트 하나가 파일시스템 수준에서는 여러 번의 쓰기가 될 수 있습니다. WAL이나 체크포인트가 잘못된 건 아닙니다. 작고 시끄러운 이벤트를 쉴 새 없이 밀어 넣을 때 문제가 드러납니다.

### SSD 단계

SSD는 작은 페이지 단위로 쓰지만 지울 때는 훨씬 큰 블록 단위로 지웁니다. 블록 일부만 바뀌면 컨트롤러는 새 데이터를 다른 위치에 쓰고, 기존 데이터를 무효 처리한 뒤, 나중에 유효한 페이지를 옮기고 블록을 지웁니다. 이것이 가비지 컬렉션입니다. 특정 영역만 먼저 닳지 않도록 쓰기 위치를 분산하는 웨어 레벨링도 함께 돌아갑니다.

둘 다 필요한 기능이긴 한데, 그 탓에 플래시 메모리에는 운영체제가 요청한 것보다 더 많은 물리적 쓰기가 일어날 수 있습니다. 이 비율을 쓰기 증폭 계수(write amplification factor)라고 부릅니다. 값은 드라이브, 여유 공간, 작업 패턴, 컨트롤러에 따라 다릅니다. 이번 사례에서는 실제 증폭 배율을 측정하지 않았으므로, 추정한 물리적 마모량을 정확한 수치로 받아들이면 안 됩니다.

그래도 방향만큼은 분명합니다. 작고 무작위적인 쓰기가 끊임없이 반복되는 작업은 SSD가 가장 힘들어하는 유형 중 하나입니다.

## 640TB면 위험한가

위험할 수 있습니다.

SSD 내구성은 보통 TBW(Terabytes Written)로 표기합니다. 일반 소비자용 1TB SSD는 수백 TBW 수준인 경우가 많고, 엔터프라이즈 제품은 훨씬 높습니다. 정확한 값은 모델, 용량, NAND 종류, 보증 조건에 따라 다릅니다.

TBW에 도달한다고 바로 고장 나는 건 아닙니다. 보증과 내구성의 기준일 뿐 카운트다운 타이머가 아니고, 그 이상 버티는 드라이브도 많습니다. 다만 백그라운드 개발 도구 하나가 수백 TB를 쓴다면 진지하게 볼 일입니다. 디스크가 차지도 않고 눈에 띄는 고장도 없는 사이에 드라이브의 쓰기 수명이 상당 부분 깎여 나갈 수 있으니까요.

## 내 PC 점검하기

순서가 중요합니다. 먼저 업데이트하고, 실제 I/O를 보고, 마지막으로 드라이브 자체 기록을 확인합니다.

### 1단계: Codex 업데이트

원문이 인용한 조사는 **0.142.0**을 로깅 감소가 들어간 버전으로 봅니다. 최신 릴리스 노트와 설치된 버전을 확인한 뒤, 측정 전에 먼저 업데이트하세요.

Codex CLI, 데스크톱 앱, 에디터 연동은 각자 다른 일정으로 배포되거나 구성 요소를 따로 번들할 수 있습니다. 하나를 업데이트했다고 로컬의 모든 Codex 관련 프로세스가 최신이 되는 건 아닙니다.

### 2단계: 로그 파일 찾기

macOS·Linux:

```bash
ls -la ~/.codex/logs_2.sqlite*
```

Windows PowerShell:

```powershell
Get-Item "$env:USERPROFILE\.codex\logs_2.sqlite*"
```

DB 파일과 함께 `-wal`, `-shm` 파일이 보일 수 있습니다. 크기만 보고 끝내면 안 됩니다. 이번 일이 오랫동안 묻혔던 이유가 바로 작은 파일 크기였습니다.

### 3단계: 실제 쓰기량 관찰

Linux에서는 `pidstat`으로 어떤 프로세스가 쓰는지 볼 수 있습니다.

```bash
pidstat -d 5
```

어떤 프로세스가 DB를 열고 있는지는 이렇게 확인합니다.

```bash
sudo lsof ~/.codex/logs_2.sqlite
```

macOS에서는 **활성 상태 보기(Activity Monitor)**의 **디스크** 탭에서 작업 중 Codex 관련 프로세스의 쓰기 바이트를 지켜보면 됩니다. Windows에서는 **리소스 모니터**나 작업 관리자의 디스크 열을 보세요. 시작 직후 잠깐 튀는 값이 아니라 지속적인 프로세스별 쓰기량을 봐야 합니다.

### 4단계: 드라이브 누적 쓰기 카운터 확인

현실에 가장 가까운 숫자는 드라이브가 직접 기록한 값입니다.

Linux나 macOS에 smartmontools가 설치돼 있다면 NVMe 드라이브는 보통 이렇게 확인합니다.

```bash
sudo smartctl -a /dev/nvme0
```

확인할 항목은 다음과 같습니다.

- **Data Units Written**
- **Percentage Used**
- 경고 또는 치명적 상태 표시

Windows에서는 CrystalDiskInfo가 **Total Host Writes**와 상태 정보를 보여줍니다. PowerShell로도 일부 상태를 볼 수 있습니다.

```powershell
Get-PhysicalDisk | Get-StorageReliabilityCounter |
  Select-Object DeviceId, Wear, Temperature
```

누적 쓰기량은 **내 드라이브 정확한 모델**의 TBW와 비교해야 합니다. 검색 결과에 나온 아무 SSD 수치와 비교하면 의미가 없습니다.

## 예전 버전을 몇 달 썼다면

당황할 필요도, 파일 크기로 짐작할 필요도 없습니다. 드라이브 카운터부터 확인하세요.

사용률(Percentage Used)이 낮고 누적 쓰기량이 사용 기간과 작업량에 비해 무난하다면 업데이트하고 넘어가면 됩니다. 마모가 유난히 높거나 경고가 떴거나 누적 쓰기량이 TBW에 비해 크다면, 중요한 데이터를 백업하고 고장 나기 전에 교체 계획을 세우는 게 좋습니다.

드라이브가 멀쩡해 보여도 백업은 해 두라는 게 원문의 조언입니다. SSD는 대개 별다른 전조 없이 고장 나기 때문입니다.

## 당장 업데이트할 수 없을 때

근본 해결책은 업데이트입니다. 아래는 업데이트 전까지 쓰기 부하를 줄이는 임시 방편입니다.

### 버려도 되는 로그는 임시 저장소로

CI 작업이나 컨테이너라면 임시 홈 디렉터리를 쓰거나 Codex 설정 디렉터리를 휘발성 저장소에 마운트하는 방법이 가장 깔끔합니다.

```bash
export HOME="$(mktemp -d)"
```

컨테이너라면 작업이 끝날 때 로컬 진단 로그가 사라져도 괜찮은 경우에 한해 Codex 상태 디렉터리에 tmpfs를 마운트할 수 있습니다. 어차피 매번 환경을 만들고 지우는 빌드 러너에 특히 잘 맞습니다.

### `/tmp`라고 다 메모리는 아니다

로그를 `/tmp`로 옮기는 방법은 `/tmp`가 실제로 메모리 기반일 때만 효과가 있습니다. 많은 Linux 시스템에서는 tmpfs일 수 있지만, macOS의 `/tmp`는 기본적으로 RAM 디스크가 아닙니다.

```bash
mount | grep ' /tmp '
```

마운트를 확인한 뒤 실제 I/O 모니터로 다시 검증하세요. 댓글에서 그럴듯해 보였다는 이유만으로 우회책을 믿으면 안 된다고 원문은 강조합니다.

### DB를 직접 고치는 건 최후의 수단

커뮤니티에는 SQLite 로그 DB를 수정해 삽입을 무시하게 만드는 방법도 돌고 있습니다. 급할 때는 쓸모가 있지만, 앱 내부 파일을 비공식적으로 건드리는 일입니다. 이후 버전에서 스키마가 바뀔 수도 있고, 앱이 DB가 정상이라는 전제로 동작할 수도 있습니다.

이 방법을 쓴다면 Codex를 먼저 종료하고, DB를 복사해 두고, 무엇을 바꿨는지 기록하고, 수정된 버전으로 올라가면 원래대로 되돌려야 합니다.

## 도구를 만드는 쪽이 얻을 교훈

원문은 이 문제가 CLI 하나에 국한되지 않는다고 봅니다.

- **디스크 사용량이 아니라 쓰기량을 재야 한다.** 로컬에 무언가를 저장하는 기능이라면 실제 사용 환경에서 시간당·세션당·일당 쓰기 바이트를 테스트해야 합니다. DB, 캐시, 인덱스, 로그 로테이션은 파일 크기만으로 평가할 수 없습니다.
- **TRACE는 의도적으로 켜는 것이어야 한다.** 상세 로그는 명시적으로 켜고 쉽게 끌 수 있어야 합니다. 기본으로 켜 두면 모든 사용자 환경이 디버깅 환경이 됩니다.
- **표준 설정은 끝까지 적용돼야 한다.** 생태계에 표준 로그 설정이 있다면 모든 싱크가 따라야 합니다. 일부만 적용되면 숙련된 사용자에게 잘못된 안도감을 줍니다.
- **구조화된 로그에도 저장 비용이 있다.** SQLite, RocksDB, 로컬 검색 인덱스, 캐시 모두 좋은 도구지만 고빈도 쓰기에는 대가가 따릅니다. 배압(backpressure), 배치 처리, 속도 제한, 보관 정책, 극단적으로 시끄러운 상황에 대한 테스트가 필요합니다.
- **개인정보와 마모는 연결돼 있다.** 원시 운영 정보를 많이 기록할수록 쓰기량도 늘고 로컬에 남는 민감한 데이터도 늘어납니다. 파일 경로, 전송 프레임, 저수준 이벤트 페이로드 기록은 배경 소음이 아니라 의식적인 디버깅 선택이어야 합니다.

## 사용자가 들일 만한 습관

> 오래 켜 두는 개발 도구를 새로 설치했다면, 쓰기 속도를 한 번은 확인해 본다.

활성 상태 보기, 리소스 모니터, `pidstat`으로 2분만 지켜봐도 의외로 많은 것을 잡아낼 수 있습니다. SSD 누적 쓰기량도 가끔 확인하고, 도구는 최신으로 유지하세요. 파일 크기가 일정하다는 건 저장량에 대한 정보일 뿐, I/O에 대한 정보가 아닙니다.

## 확인된 것과 아직 불확실한 것

원문은 근거로 삼은 조사의 한계도 분명히 밝힙니다.

- 37TB는 사용량이 많은 한 사용자의 머신에서 나온 값입니다. 하나의 데이터 포인트일 뿐 일반적인 수치가 아닙니다.
- 가장 상세한 로그 레벨이 언제부터 적용됐는지는 보고마다 다릅니다. 정확한 시작 시점은 불확실합니다.
- 연 640TB는 21일 표본을 바탕으로 한 단순 계산이지 예측치가 아닙니다.
- SSD 쓰기 증폭은 실제로 일어나지만, 이번 사례의 물리적 NAND 증폭 배율은 측정하지 않았습니다.
- 0.142.0 이후 85% 감소는 초기 관찰 결과이며, 모든 플랫폼과 작업 환경에서 보장되는 수치가 아닙니다.

그래도 대응 방법은 같습니다. 업데이트하고, 프로세스 쓰기량을 재고, 드라이브 카운터를 확인하는 것입니다.
