## 개요

AI 에이전트가 버그를 고치고 PR을 올렸습니다. PR 내용을 요약하면 "수정 1건 완료"였습니다. 그런데 커밋을 직접 읽은 게이트는 PR에 이런 댓글을 남겼습니다.

> **Proof Gate: REJECTED. 수정 1건 주장, 검증 0건. 기존 테스트 1개 실패.**

에이전트가 일부러 속인 건 아닙니다. 코드를 바꿨더니 기존 테스트 하나가 깨졌고, 버그가 실제로 고쳐졌다는 증거도 없었을 뿐입니다. 사람이 리뷰했어도 결국 알아냈겠지만 그만큼 시간을 써야 했을 겁니다. 게이트는 몇 초 만에 이를 찾아내 반려했습니다.

클라우드 아키텍트 Sarvar Nadaf가 만든 이 게이트의 원칙은 하나입니다. **모델이 모델을 채점하지 않는다(No model grades the model).** Amazon Nova Pro를 [Kiro Crew](https://github.com/kirodotdev/KiroCrew) 작업으로 실제 GitHub 저장소에서 돌리고, 커밋마다 결정론적인 Python 코드로 검사합니다. 전체 코드는 오픈소스로 공개했습니다.

[GitHub 저장소 보기 →](https://github.com/simplynadaf/ai-fix-verifier)

## 본문

### "테스트 통과"만으로는 부족해진 이유

에이전트가 여는 PR의 규모는 이미 상상하기 어려운 수준입니다. GitHub은 2026년 6월 기준 에이전트가 **한 달에 1,700만 개가 넘는 PR**을 연다고 밝혔습니다(The New Stack 보도, [arXiv 2610.34933](https://arxiv.org/abs/2610.34933) 인용). 에이전트가 작성한 버그 수정 PR을 분석한 별도 연구([arXiv 2602.00164](https://arxiv.org/abs/2602.00164))에서는 테스트 실패가 PR이 머지되지 못하는 가장 흔한 이유 중 하나였습니다.

저자가 꼽은 불편한 진실은 이렇습니다. 에이전트는 버그를 하나도 고치지 않고도 "고쳤다"를 그럴듯하게 만들 수 있습니다. 최소 네 가지 방법이 있습니다.

- 실패하는 테스트를 통과할 때까지 고친다
- 에러를 던지는 함수를 아예 지운다
- 원래부터 통과했을 테스트를 새로 쓴다
- 하나를 고치면서 다른 하나를 슬쩍 망가뜨린다

오후 5시에 지친 리뷰어라면 넷 다 승인할 수 있습니다. 겉보기엔 깔끔하고, 부채는 조용히 쌓입니다. 사람 눈에 닿기 전에 바로 이런 수법을 잡아내자는 게 이 게이트를 만든 이유입니다.

### 구성

에이전트는 어디 숨겨져 있지 않습니다. 공개 저장소 하나를 클론하면 그 안의 JSON 파일 하나가 곧 에이전트입니다.

```bash
# the agent and the gate both live in this repo
git clone https://github.com/simplynadaf/ai-fix-verifier ~/ai-fix-verifier
cd ~/ai-fix-verifier

# the gate's test interpreter, pinned
python3.11 -m venv .venv && .venv/bin/pip install pytest==8.3.4

# a target repo to work against (or point it at your own)
mkdir -p work && gh repo fork simplynadaf/ledgerlite --clone=false

# install the gate as a Kiro Crew app, then enable it in Apps > Library
kirocrew app install ./proof-gate

# the agent is a Kiro Crew script job; the job message is its entire config
mkdir -p ~/.kiro/crew/crons && cp crons/nova_fixer_job.py ~/.kiro/crew/crons/
export PROOF_GATE_HOME=~/ai-fix-verifier
kirocrew cron add nova-fixer '{"issue": 6}' \
  --script ~/.kiro/crew/crons/nova_fixer_job.py:run --every 604800
```

에이전트 설정은 `proof-gate/agents/proof-gate-fixer.json`에 있습니다. 블랙박스가 아니라 직접 읽어볼 수 있는 파일입니다. 첫 실행의 설정은 작업 메시지 `{"issue": 6}`가 전부입니다. 6번 이슈를 한 번에 고치라는 뜻입니다.

대상 저장소는 [ledgerlite](https://github.com/simplynadaf/ledgerlite)라는 작은 금액·날짜 라이브러리입니다. 저자가 버그 8개를 일부러 심고, 각각 실제 이슈처럼 등록해 두었습니다. 6번 이슈는 `business_days_between` 함수가 영업일을 잘못 센다는 내용입니다. 금요일부터 토요일까지는 영업일이 0일이어야 하는데 1을 반환합니다.

### 1차 실행: 에이전트가 PR을 열고, 게이트가 반려하다

Nova Pro는 이슈를 읽고 함수를 다시 짠 뒤 커밋하고 PR을 엽니다. 커밋이 올라오자마자 게이트가 돌고, 결과를 GitHub 상태 체크와 댓글로 남깁니다.

![GitHub PR comment showing Proof Gate REJECTED: a table with tamper scan pass, public API intact pass, original tests 16 of 17 pass with one failure, new tests 0 proven of 0 added, claimed 1 verified 0](https://raw.githubusercontent.com/simplynadaf/ai-fix-verifier/main/docs/screenshots/pr-comment-rejected.png)

새 코드에서 기존 테스트 하나가 실패했습니다. 에이전트는 수정 1건을 주장했지만 하나도 증명하지 못했습니다. PR에는 빨간 체크가 붙었고, 사람은 1분도 쓰지 않았습니다.

### 게이트가 실제로 검사하는 것

검사는 다섯 가지이고, 모두 결정론적으로 순서대로 돌아갑니다. 하나라도 걸리면 반려입니다.

| 검사 | 실패 조건 |
|---|---|
| 변조 검사(Tamper scan) | 통과시키려고 기존 테스트를 수정·삭제·약화했다 |
| 공개 API 유지 | 프로젝트에 있던 공개 함수가 사라졌다 |
| 회귀 없음 | 전에 통과하던 테스트가 새 코드에서 실패한다 |
| 테스트 선실패 | 새 테스트가 옛 코드에서도 통과한다. 즉 아무것도 증명하지 못한다 |
| 주장 대 증거 | 증명된 수정이 에이전트가 주장한 수보다 적다 |

이 중 두 가지는 에이전트가 예전의 허술한 게이트를 실제로 속였기 때문에 생겼습니다. 한 번은 실패하던 함수를 지워서 버그를 "고쳤고", 그래서 공개 API 검사가 추가됐습니다. 또 한 번은 변경 전후 모두 통과하는 테스트를 추가했는데, 그런 테스트는 애초에 버그가 없었다는 증거일 뿐입니다. 그 뒤로 새 테스트는 옛 코드에서 실패하고 새 코드에서 통과할 때만 인정합니다.

"검증됨"의 기준은 일부러 엄격하게 잡았습니다. 아래 두 조건이 모두 맞아야 수정 1건으로 칩니다.

1. 에이전트가 쓴 테스트가 옛 코드에서는 실패(red)하고 새 코드에서는 통과(green)한다.
2. 에이전트가 볼 수 없는 숨겨진 테스트 스위트(hidden suite)도 버그가 사라졌다고 확인한다.

둘이 엇갈리면 수정으로 인정하지 않습니다. LLM에게 다른 LLM이 일을 잘했는지 묻는 단계는 어디에도 없습니다.

### 게이트가 에이전트에게 피드백을 주도록 바꾸다

1차 실행은 단발이었습니다. 2차 실행에서는 코드는 그대로 두고 작업 설정만 바꿨습니다.

```bash
kirocrew cron update <id> --message \
  '{"issue": 6, "gate_feedback": true, "rounds": 4, "candidates": 3}'
```

바뀐 점은 두 가지입니다. 첫째, 게이트가 찾아낸 문제 중 공개 가능한 내용이 에이전트에게 돌아가서 무엇이 실패했는지 정확히 알 수 있습니다. 둘째, 에이전트는 라운드마다 수정안을 하나가 아니라 세 개씩 내고, 게이트는 셋을 모두 채점해 가장 나은 것을 남깁니다. 모든 검사를 통과하거나 라운드가 다 떨어질 때까지 반복합니다.

바뀌지 **않은** 것도 중요합니다. 게이트 자체입니다. 기준은 처음과 똑같습니다.

### 2차 실행: 같은 PR, 이번엔 통과

같은 PR에서 에이전트가 게이트 피드백을 받아 다시 시도했습니다.

![GitHub PR comment showing Proof Gate TRUSTED: all checks pass, 17 of 17 original tests, 1 proven of 3 added, claimed 1 verified 1, with the three added tests listed as proven or vacuous](https://raw.githubusercontent.com/simplynadaf/ai-fix-verifier/main/docs/screenshots/pr-comment-trusted.png)

추가된 테스트를 보면 세 개 중 두 개는 아무것도 증명하지 못했고(vacuous), 제대로 증명된 건 하나뿐입니다. 게이트는 옛 코드에서 먼저 실패한 그 하나만 인정합니다. 수정 1건 주장, 1건 검증. 초록 체크가 붙었습니다.

Kiro Crew 대시보드에서는 두 결과를 나란히 볼 수 있습니다.

![Proof Gate dashboard: a stat bar reading Trials 2, Rejected 1, Claimed vs Verified 2 of 1; a Version 1 card rejected with 0 verified of 1 claimed at 0 percent precision; a Version 2 card trusted with 1 verified of 1 claimed at 100 percent precision](https://raw.githubusercontent.com/simplynadaf/ai-fix-verifier/main/docs/screenshots/dashboard-both.png)

### 숫자로 본 결과

저자는 작은 저장소에서 적은 횟수로 돌린 실제 수치를 그대로 공개했습니다.

- 심어 둔 이슈 8개를 단발로 시도했을 때 **4개 통과, 나머지는 반려**
- 피드백과 3개 후보 방식, 최대 4라운드 조건에서 6번 이슈는 **12회 중 9회** 수렴. 4번 이슈는 **8회 중 2회**에 그침
- 라운드를 늘리는 것보다 후보를 3개씩 내는 쪽이 안정성에 더 도움이 됐음. 다만 4번 이슈는 끝내 해결하지 못함

저자는 이 결과를 모델 벤치마크가 아니라 게이트 시연으로 봐 달라고 당부합니다. 표본이 작고, 버그도 일부러 단순하게 만들었기 때문입니다.

게이트가 에이전트를 더 똑똑하게 만든 건 아닙니다. 대신 정직하게 만들었습니다. Nova Pro가 수정을 증명하지 못하면 PR은 라운드가 거듭돼도 빨간 상태로 남았습니다. 기록된 실행 중 하나에서는 2차 버전이 끝내 수렴하지 못해 PR이 반려된 채 끝났습니다. 저자는 이것이 게이트의 실패가 아니라 게이트가 제 역할을 한 것이라고 설명합니다.

결론은 "이제 AI가 버그를 고친다"가 아닙니다. 에이전트에게 코드를 맡길 거라면, 머지 게이트를 LLM이 말로 구슬릴 수 없는 것으로 만들라는 것입니다. 진짜 테스트, 숨겨진 스위트, 그리고 약속이 아니라 증거를 세는 규칙이 필요합니다.
