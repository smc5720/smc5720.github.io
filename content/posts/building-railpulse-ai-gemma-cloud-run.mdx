## 개요

AI/ML 분야 Google Developer Expert(GDE)인 로비나 미르바하르(Robina Mirbahar)가 철도 관제용 AI 에이전트 **RailPulse AI**를 오픈소스로 공개했습니다. 아제르바이잔 ADA 대학교에서 열린 **DevFest Baku 2026** 워크숍에서 직접 만들고 배포해 보인 프로젝트입니다.

RailPulse AI는 열차 위치를 실시간으로 추적하고 관제 권고안을 내놓습니다. 추론은 Google의 오픈 웨이트 모델 **Gemma**가 맡고, 에이전트 구성은 **Google Agent Development Kit(ADK)**, 배포는 **Google Cloud Run**으로 처리했습니다. 미르바하르가 가장 강조한 원칙은 하나입니다. 사람의 안전이 걸린 결정을 LLM 혼자 내리게 두지 않는다는 것입니다.

## 본문

### 챗봇 데모와 실제 산업 현장은 다르다

AI 튜토리얼은 대부분 시를 쓰거나 PDF를 요약하거나 보일러플레이트 코드를 만드는 챗봇을 다룹니다. 미르바하르는 이런 데모가 재미는 있어도 미션 크리티컬 산업의 현실과는 거리가 멀다고 지적합니다.

수천 km를 달리는 화물열차처럼 물리적인 시스템을 AI로 운영하면, 범용 챗봇은 쓸모가 없는 정도를 넘어 위험해질 수 있습니다. 환각으로 지어낸 제한 속도 하나, 늦게 도착한 신호 경보 하나가 장비 고장이나 탈선으로 이어질 수 있기 때문입니다.

철도 관제사가 계속 지켜봐야 하는 정보는 크게 세 가지입니다.

- **실시간 텔레메트리:** GPS 좌표, 차축 베어링 온도, 기관차 속도
- **노선 기상:** 해안이나 산악 구간에서 갑자기 부는 측풍
- **운행 일정 복구:** 지연 시간, 승객 환승 마감, 단선 구간의 교행 측선 사이에서 균형 잡기

비상 상황에서 관제사는 흩어진 SCADA 대시보드와 수천 줄짜리 로그를 뒤질 시간이 없습니다. 실시간 데이터를 모으고, 신호 규칙과 대조하고, 바로 실행할 수 있는 권고안을 정리해 주는 시스템이 필요합니다. 여기에 **환각이 있어서는 안 된다**는 조건이 붙습니다. LLM의 유연한 추론과 하드코딩한 안전 규칙의 예측 가능성을 함께 갖춰야 하는 이유입니다.

### 추측 대신 도구 호출로 사실을 가져온다

RailPulse AI는 Gemma가 철도 상황을 짐작하게 두지 않습니다. ADK의 함수 호출(function calling) 기능으로 전용 텔레메트리 도구를 붙였습니다.

```python
def get_live_train_telemetry(train_id: str) -> dict:
    """Fetch live GPS, speed, bearing temperatures, and locomotive health."""
    pass

def check_corridor_signals_and_wind(corridor_id: str) -> dict:
    """Query wayside signal states (Green/Yellow/Red) and track anemometers."""
    pass

def calculate_schedule_recovery(train_id: str, current_delay_min: int) -> dict:
    """Calculate speed profiles needed to recover schedule without exceeding corridor limits."""
    pass
```

예를 들어 운영자가 이렇게 묻는다고 해 봅시다.

> *"102번 열차가 압셰론(Absheron) 구간에 14분 늦게 진입하고 있습니다. 속도를 올려서 지연을 만회할 수 있을까요?"*

Gemma는 답부터 내놓지 않습니다. 먼저 `check_corridor_signals_and_wind(corridor="Absheron")`와 `get_live_train_telemetry(train_id="102")`를 스스로 호출해 현재 상태를 확인하고, 그 결과를 근거로 응답을 만듭니다.

### 최종 안전 판단은 LLM이 아니라 코드가 내린다

미르바하르는 물리 시스템에서 **사람의 생명이 걸린 결정을 LLM에게만 맡겨서는 안 된다**고 강조합니다. 모델이 잠깐 맥락을 혼동하면 풍속 90km/h 폭풍 속에서 시속 140km를 유지하라고 권할 수도 있습니다. 그래서 RailPulse AI는 판단을 두 층으로 나눴습니다.

1. **1단계(인지적 추론):** Gemma가 상황을 분석하고 맥락을 뽑아내 일정 복구 계획을 제안합니다.
2. **2단계(결정론적 가드레일):** 하드코딩한 파이썬 인터록이 권고안을 물리적 불변 조건과 대조한 뒤에 내보냅니다.

```python
class SafetyInterlock:
    MAX_HIGH_WIND_SPEED_KMH = 80.0
    HIGH_WIND_THRESHOLD_KMH = 65.0

    @classmethod
    def enforce_guardrails(cls, advisory: RailDispatchAdvisory, wind_speed: float, signal_state: str) -> RailDispatchAdvisory:
        # Rule 1: High Wind Speed Clamp
        if wind_speed >= cls.HIGH_WIND_THRESHOLD_KMH:
            if advisory.recommended_speed_kmh > cls.MAX_HIGH_WIND_SPEED_KMH:
                advisory.recommended_speed_kmh = cls.MAX_HIGH_WIND_SPEED_KMH
                advisory.safety_flags.append(
                    f"GUARDRAIL ENFORCED: Wind speed {wind_speed} km/h exceeds threshold. Speed clamped to 80 km/h."
                )

        # Rule 2: Absolute Red Signal Override
        if signal_state == "RED":
            advisory.recommended_speed_kmh = 0.0
            advisory.action_required = "EMERGENCY_STOP"
            advisory.safety_flags.append("CRITICAL: Red signal detected. Immediate stop enforced.")

        return advisory
```

규칙은 두 가지입니다. 풍속이 65km/h 이상이면 권장 속도를 80km/h 이하로 묶고, 적색 신호가 잡히면 무조건 속도를 0으로 만들어 비상 정지를 지시합니다. 운영자의 무리한 요청이나 예상하지 못한 프롬프트가 모델을 안전 범위 밖으로 밀어붙여도 이 가드레일은 우회할 수 없다고 미르바하르는 설명합니다.

### Pydantic으로 출력 형식을 강제한다

자유 형식 텍스트 때문에 운영자 대시보드가 멈추는 일을 막으려고, 에이전트의 모든 권고안은 엄격한 스키마로 검증합니다.

```python
from pydantic import BaseModel, Field
from typing import List, Optional

class RailDispatchAdvisory(BaseModel):
    train_id: str
    recommended_speed_kmh: float = Field(..., ge=0.0, le=160.0)
    delay_delta_minutes: int
    signal_status: str
    action_required: str
    advisory_summary: str
    safety_flags: List[str] = []
    confidence_score: float = Field(..., ge=0.0, le=1.0)
```

권장 속도는 0~160km/h, 신뢰도 점수는 0~1 범위로 제한합니다. 응답이 이 구조에 맞지 않으면 ADK 파이프라인이 관제 화면에 도달하기 전에 걸러냅니다.

### 왜 Cloud Run인가

RailPulse AI는 Docker 컨테이너로 패키징해 Google Cloud Run에 배포했습니다. 미르바하르가 꼽은 이유는 다음과 같습니다.

- **서버리스 비용 구조:** 철도 텔레매틱스 트래픽은 열차 도착이나 차량기지 입환 때 몰리고 그 사이에는 한산합니다. Cloud Run은 0에서부터 트래픽에 맞춰 늘어났다가 다시 줄어듭니다.
- **폐쇄망·데이터 주권 환경 대응:** Gemma는 오픈 웨이트 모델이라 추론 전체를 자체 VPC 안에서 돌릴 수 있습니다. 민감한 운행 데이터를 외부 상용 API로 보낼 필요가 없습니다.
- **명령 한 줄로 배포:**

```bash
gcloud run deploy railpulse-agent \
    --source . \
    --platform managed \
    --region europe-west1 \
    --allow-unauthenticated \
    --memory 4Gi \
    --cpu 2
```

### 영어·아제르바이잔어·러시아어 동시 지원

카스피해 횡단 국제운송로(Trans-Caspian International Transport Route) 같은 국제 물류 노선에서는 운영자들이 여러 언어를 씁니다. RailPulse AI는 Gemma의 다국어 능력을 살려 텔레메트리 수치, 안전 플래그, 권고 요약을 영어, 아제르바이잔어(Azərbaycan dili), 러시아어(Русский)로 보여 줍니다. 현지 관제사는 모국어로 시스템을 쓰고, 안전 규칙은 내부에서 언어와 상관없이 똑같이 적용됩니다.

### 미르바하르가 정리한 세 가지 교훈

1. **에이전트는 프롬프트 이상의 것이다.** 프로덕션 에이전트는 프롬프트 엔지니어링이 20%, 시스템 엔지니어링이 80%입니다. 도구 정의, 스키마 검증, 네트워크 복원력, 오류 처리가 여기에 들어갑니다.
2. **결정론적 가드레일은 선택이 아니라 필수다.** 물리·산업·의료 분야에서는 LLM에게 검증 없는 권한을 주면 안 됩니다. 추론은 모델에, 최종 안전 판단은 코드 인터록에 맡겨야 합니다.
3. **오픈 웨이트 모델은 프로덕션에 쓸 만하다.** Gemma 같은 모델과 Cloud Run 같은 서버리스 플랫폼을 쓰면, 개인 개발자든 기업 팀이든 상용 API에 수천 달러를 쓰지 않고도 비공개로 운영하고 감사(audit)할 수 있는 AI 시스템을 만들 수 있습니다.
