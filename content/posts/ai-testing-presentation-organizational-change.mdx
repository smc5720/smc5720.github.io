## 개요

필자 xulingfeng은 직접 만든 멀티 에이전트 기반 자동화 테스트 시스템을 소개하려고 사내 발표를 열었다. 처음 계획은 AI로 테스트 효율을 얼마나 높일 수 있는지 보여주는 자리였다.

그런데 2026년 11월 5일 열린 이 세션은 테스트 이야기로 끝나지 않았다. 제품·개발·QA가 어떻게 함께 일해야 하는지, 요구사항은 왜 자꾸 어긋나는지, AI 시대에 엔지니어링 조직을 어떻게 꾸려야 하는지로 대화가 넓어졌다. 결국 이 자리는 회사의 조직 개편을 실제로 출발시키는 마지막 계기가 됐다.

필자는 "테스터가 AI로 더 효율적으로 일하게 돕자고 시작했는데, 정작 AI 때문에 조직 전체가 일하는 방식을 다시 생각하게 됐다"고 돌아봤다.

## 요구사항부터 회귀 테스트까지 AI에 맡기다

![I Wanted AI to Handle the Entire Testing Process](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/s78tfnz0j01d5fhebhjf.png)

필자가 원한 건 테스트 케이스로 자동화 스크립트를 뽑아주는 수준이 아니었다. 요구사항 이해, 테스트 설계, 실행, 결함 보고, 수정 확인, 회귀 테스트까지 전 과정을 하나로 잇는 것이 목표였다. 현재 구성한 흐름은 대략 이렇다.

1. AI가 제품 요구사항 문서(PRD)와 프로토타입을 읽고 업무 흐름과 인수 조건을 파악한다.
2. 테스트 케이스를 만들고, 여러 에이전트가 이를 검토한다.
3. 테스트 케이스에 맞춰 AI가 웹 브라우저와 모바일 앱을 직접 조작하며 실제 사용자처럼 테스트한다.
4. 문제를 발견하면 결함 리포트를 작성해 이슈 트래커에 등록한다.
5. 등록된 결함은 2차 검토와 사람의 확인을 거쳐 담당 개발자에게 배정된다.
6. 개발자가 수정하면 AI가 회귀 테스트를 돌려 수정 여부를 확인하고, 사람의 감독 아래 결함 종료 절차를 진행한다.

요구사항부터 회귀 테스트까지 이어지는 이 흐름은 이미 실제로 돌아가고 있다.

필자가 가장 크게 체감한 변화는 UI 자동화의 고질적인 문제, 즉 유지보수 부담이 줄었다는 점이다. 기존에는 개발자가 UI 컴포넌트 하나만 바꿔도 테스터가 요소 로케이터, 페이지 객체, 인터랙션 스크립트를 다시 손봐야 했다. 화면이 자주 바뀔수록 비용은 커졌고, 테스트를 돌리는 시간보다 스크립트를 고치는 시간이 더 길어지기도 했다.

지금은 AI가 현재 화면을 보고 요소와 상태를 파악한 뒤, 테스트 목적에 맞게 알아서 동작을 수행한다. UI 변경이나 실행 실패에 여전히 대응해야 하지만, 예전에 사람이 반복해서 고쳐야 했던 작업의 상당 부분을 AI가 가져갔다.

## 정해진 케이스를 넘어서는 탐색형 테스트

필자는 오랫동안 "자동화는 회귀 테스트엔 쓸모 있지만 새 결함을 찾는 데는 약하다"고 생각했다. 기존 자동화 테스트는 미리 설계한 케이스, 고정된 실행 단계, 정해진 단언(assertion)에 기대기 때문이다. 알려진 경로는 반복할 수 있어도, 아무도 떠올리지 못한 문제는 찾지 못한다. 탐색하는 테스터라기보다 지시를 따르는 실행기에 가까웠다.

요구사항을 이해하고 화면을 관찰하며 상황에 따라 행동을 바꾸는 AI 에이전트가 나오면서 생각이 바뀌었다. 필자는 에이전트를 다듬으면서 한 가지 원칙을 강조했다.

> 요구사항 문서만 따르지 말 것. 테스트 케이스를 탐색의 한계로 여기지 말 것.

그래서 AI는 요구사항에 정의된 테스트를 마친 뒤에도 다음 같은 시나리오를 추가로 살핀다.

- **잘못되거나 예상 밖의 입력:** 빈 값, 지나치게 긴 텍스트, 허용되지 않는 문자, 특이한 형식, 의외의 데이터 조합
- **경계 조건:** 최댓값·최솟값, 임계값, 중복 제출, 비정상적인 조작 순서
- **비정상 흐름:** 작업 중단, 반복 클릭, 새로고침, 네트워크 장애, 세션 만료, 단계 간 상태 불일치
- **보안 관련 시나리오:** 무단 접근, 권한 경계, 민감 정보 노출, 허용되지 않은 작업 시도
- **예상 밖 인터랙션:** 정상 단계 건너뛰기, 빠른 연속 조작, 상태 반복 전환, 다른 진입점으로 같은 기능 접근

물론 AI가 운영 시스템을 마음대로 건드리게 두자는 뜻은 아니다. 탐색 범위, 테스트 환경, 계정 권한, 운영 리스크를 모두 통제해야 하고, 보안 테스트는 명확히 허가된 범위 안에서만 해야 한다고 필자는 선을 그었다.

필자의 결론은 이렇다. 예전 자동화는 이미 아는 문제를 반복 확인하는 데 그쳤다면, 이제 AI는 우리가 찾을 생각조차 못 한 문제를 발견하는 데 도움을 줄 수 있다. 모든 결함을 찾아준다는 보장도 없고 사람의 판단을 대신하지도 못하지만, 자동화 테스트가 더는 미리 써둔 케이스에 갇혀 있을 필요는 없다는 것이다.

## 밤에는 AI가 일하고, 낮에는 사람이 판단한다

![AI Works at Night. Humans Make the Decisions During the Day.](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/j41f60cagoqhjlqeu0ty.png)

요즘 필자는 퇴근 전에 자동화 테스트 작업을 예약해 둔다. 에이전트는 밤새 테스트를 돌리고, 다음 날 아침 출근하면 AI가 올린 결함 리포트가 한 묶음 쌓여 있다. 필자는 이를 하나씩 보면서 실제 문제인지, 현재 요구사항과 맞는지 판단한 뒤 확정하고 담당 개발자에게 넘긴다.

테스터가 시간을 쓰는 방식이 달라졌다. 시스템을 조작하고, 케이스를 실행하고, 결과를 보고, 보고서를 쓰는 반복 작업은 상당 부분 AI가 맡는다. 사람은 이슈를 평가하고 리스크를 분석하며 품질을 높이는 일에 더 집중한다.

다만 이 과정에서 새로운 문제가 보였다. **결함을 찾는 것과 그 결함을 잘 전달하는 것은 별개**라는 점이다. 초기 AI 결함 리포트는 정보는 많았지만 빽빽한 텍스트 덩어리여서 개발자가 읽기 불편했다. 필자는 리포트 형식을 여러 차례 고쳤다. 실행 중 일어난 일을 전부 늘어놓는 대신, 무슨 일이 어디서 일어났는지, 기대 동작과 실제 동작이 어떻게 다른지, 어떻게 재현하고 확인할 수 있는지를 명확히 담도록 했다. 몇 번의 수정 끝에 리포트는 훨씬 읽기 쉽고 쓸모 있어졌다.

필자는 여기서 AI 결과물의 품질을 처리한 작업량만으로 재선 안 된다고 짚는다. 다음 단계에 있는 사람이 그 결과를 실제로 쓸 수 있는지도 따져야 한다는 것이다.

테스트 사이클이 끝날 때마다 AI에게 그 회차의 문제와 교훈을 정리하게 하고, 검토와 검증을 거쳐 재사용 가치가 확인된 내용은 범용 Skill로 만든다. 다음 사이클은 처음부터 시작하지 않고 이전 회차의 학습 위에서 출발한다.

**실행 → 문제 발견 → 검토 → 교훈 정리 → 재사용 가능한 지식을 Skill로 → 다음 사이클 시작**

## 숫자로 본 성과, 그리고 드러난 한계

![The Numbers Show the Value, but Also Reveal Problems](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/kf4xwiw0yo3qgzoezfxo.png)

필자가 공개한 한 지식 베이스 프로젝트의 결과는 다음과 같다.

| 항목 | 결과 |
|:--|--:|
| 발견된 전체 결함 | 47건 |
| AI가 발견한 결함 | 36건 |
| 사람이 발견한 결함 | 11건 |
| 최종 유효 결함으로 확정 | 30건 |
| 그중 AI가 발견한 유효 결함 | 21건 |

최종 확정된 유효 결함 30건 가운데 21건, 즉 **70%**를 AI가 찾아냈다. 필자는 이 프로젝트와 해당 테스트 범위 안에서 AI가 단순히 케이스를 실행하는 도구를 넘어 실제 결함 발견에 기여하고 있다고 평가했다.

API 쪽 실험도 진행 중이다. 에이전트가 페이지를 탐색하며 업무 흐름에 엮인 API 호출을 수집하고, 매일 정해진 시간에 전수 API 검증을 돌린다. 현재 테스트 환경에서 업무 흐름과 연결된 API 약 **300개**를 다루고 있다.

한계도 분명했다. 테스트 환경이 하나뿐이라 여러 요구사항을 동시에 개발하면 코드 변경이 충돌하고, 배포가 다른 테스트를 끊어먹는다. 두 번째 테스트 환경과 성능 테스트 전용 환경을 추가하는 방안을 검토해야 한다. 여러 Windows 버전과 360 브라우저 대응 등 브라우저 호환성 테스트도 더 보강해야 한다.

필자는 이런 인프라 문제는 자원과 기술을 더 투입해 차근차근 풀 수 있다고 봤다. 정작 필자를 고민하게 만든 건 다른 종류의 문제였다.

## 자동화가 드러낸 조직의 숨은 문제

![Automation Exposes Organizational Problems That Traditional Testing Often Hides](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/vndtl61kg7z7wxlku6p8.png)

어느 순간 AI가 보고한 결함 일부가 '무효'로 분류되기 시작했다. 처음에는 AI가 요구사항을 잘못 이해했거나 테스트 로직에 문제가 있다고 의심했다.

자세히 들여다보니 AI만의 잘못이 아니었다. 제품과 개발이 논의해서 요구사항을 이미 바꿨는데, 공식 PRD는 그대로였던 경우가 있었다. 두 팀은 새로운 합의에 이르렀고 때로는 구현까지 조용히 바꿨지만, QA와 AI는 여전히 원래 문서를 기준으로 일하고 있었다.

AI는 공식 요구사항과 다른 부분을 정확히 짚었지만, 그 보고는 무효 처리됐다. 테스트 관점에서 AI가 틀린 건 아니었고, 개발팀 입장에서는 현재 구현 기준으로 고칠 필요가 없는 문제였다. 진짜 원인은 **팀이 같은 요구사항을 서로 다른 버전으로 들고 일하고 있었다**는 데 있었다.

> 자동화는 그동안 수작업 테스트가 조용히 흡수하고 가려온 조직의 문제를 드러낼 수 있다.

예전에는 테스터가 구두 소통, 그때그때의 확인, 개인 경험으로 문서의 빈틈을 메웠다. 꼭 필요한 일이지만, 그 덕분에 조직은 프로세스가 잘 돌아간다고 착각하기 쉽다. AI는 누군가의 사적인 대화도, 머릿속 최신 생각도 알지 못한다. 주어진 맥락대로 움직일 뿐이다. 공식 문서와 팀의 실제 이해가 어긋나는 순간 자동화는 그 틈을 그대로 드러낸다.

그래서 필자는 "AI가 충분히 똑똑한가"만 물어선 안 된다고 말한다. **모두가 동의하고, 최신 상태로 유지되며, AI도 올바르게 해석할 수 있는 단일한 요구사항이 팀에 있는가**를 함께 물어야 한다.

## 기술 발표가 조직 구조 논의로 번진 이유

![A speaker in a meeting](https://images.pexels.com/photos/6814337/pexels-photo-6814337.jpeg?auto=compress&cs=tinysrgb&h=650&w=940)
*Photo by [cottonbro studio](https://www.pexels.com/@cottonbro) on [Pexels](https://www.pexels.com/photo/a-speaker-in-a-meeting-6814337/)*

11월 5일 세션은 로컬 AI 에이전트와 자동화 테스트 경험을 나누는 자리였고, 회사 창업자 중 한 명도 참석했다. 처음엔 AI 테스트 역량이 주제였지만 대화는 점점 엔지니어링 워크플로와 조직 구조로 옮겨갔다.

필자가 갈수록 공감하게 된 관점은 이것이다.

> AI가 코드를 만드는 비용은 낮추고 있지만, 사람 사이의 조율 비용은 그만큼 빠르게 줄지 않는다.

기존에는 요구사항 하나가 기획자의 분석과 문서화를 거쳐 프론트엔드·백엔드 개발자에게 넘어가고, 마지막으로 QA가 검증했다. 손이 바뀔 때마다 맥락을 다시 전달해야 했고, 어느 한 곳에서라도 오해가 생기면 재작업으로 이어졌다.

이제는 AI 덕분에 기획자가 일부 코드를 직접 고칠 수 있고, 테스터가 코드를 이해하고 수정할 수 있으며, 개발자는 요구사항 분석과 제품 설계에 더 깊이 들어갈 수 있다. 코드 몇 줄이면 끝날 작은 요구사항이 여러 역할과 절차, 소통 단계를 거쳐야 한다면 조율 비용이 실제 코딩 비용을 훌쩍 넘을 수 있다.

필자는 전문 분업의 가치가 사라졌다는 뜻은 아니라고 강조한다. AI가 역할 사이의 역량 장벽을 조금씩 낮추고 있다는 것이다. 이 논의에서 나온 방향은 전통적인 역할 중심 분업에서 벗어나, AI의 도움으로 각자 역할의 경계를 넘나드는 더 유연한 구조로 가자는 것이었다.

여기서 말하는 '팀 전체의 풀스택화'는 모두가 전통적인 풀스택 엔지니어가 되거나 자기 전문성을 버리자는 의미가 아니다.

> 제품·개발·QA 누구든 AI를 활용해 기존의 기술적 경계를 넘고, 자신이 이해하는 문제를 직접 풀 수 있어야 한다.

- **기획자**는 AI로 작은 요구사항의 코드를 직접 고치고 검증한다.
- **개발자**는 요구사항 분석 단계부터 참여하고, 큰 과제는 전체를 책임진다.
- **테스터**는 결함을 찾고 리포트만 올리는 데서 멈추지 않는다. AI로 원인을 파고들고 코드도 수정하되, 개발자가 리뷰하고 확인한다.

작은 요구사항은 불필요한 인계를 줄이고, 큰 과제는 전체를 조율할 명확한 책임자를 둔다. 역할을 없애자는 게 아니라, 경직된 경계에서 새어 나가는 정보 손실을 줄이자는 취지다.

## 협업은 요구사항 단계에서 시작해야 한다

![Collaboration Should Start with Requirements, Not After Testing Finds a Problem](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/7yuq9qneaq6r7dlmnpip.png)

이렇게 일하려면 먼저 요구사항 맥락을 팀 전체가 공유해야 한다. 논의에서는 몇 가지 구체적인 방향이 나왔다.

**첫째**, PRD 작성과 개발이 다 끝난 뒤에야 테스터가 요구사항을 파악하는 구조를 버리고, 제품·개발·QA가 처음부터 요구사항 정렬에 함께 참여한다.

**둘째**, 표준화된 PRD Skill과 구조화된 템플릿을 만들어 요구사항 문서의 형식을 통일한다. 무엇보다 요구사항이 바뀌면 공식 문서를 즉시 고쳐야 한다. 변경 사항이 몇몇 사람의 사적인 대화에만 남아 있어선 안 된다.

더 과감한 아이디어도 나왔다. 스마트 사원증으로 녹음한 회의 내용에서 요구사항 변경을 감지하고, 영향을 줄 만한 부분을 표시해 PRD 수정을 돕는 방식이다. 수정안은 관련자에게 넘겨 검토·승인을 받는다. 필자는 *이것이 아직 검토 중인 아이디어일 뿐 실제로 도입한 기능은 아니라고* 분명히 했다.

원칙은 하나다. **팀이 실제로 공유하는 이해를 모두가 쓸 수 있는 형태로 제때 기록해야 한다.** PRD뿐 아니라 개발·테스트 공용 Skill, 코딩 표준, Spec도 마찬가지다. 세 역할이 어느 정도 일관된 맥락에서 일할 때 AI는 역할마다 정보 섬을 하나 더 만드는 대신, 워크플로의 각 단계를 잇는 도구가 된다.

## 개별 AI 도구에서 AI 중심 엔지니어링 체계로

논의는 결국 특정 에이전트나 테스트 도구를 넘어 엔지니어링 체계 전체로 향했다. 현재 추진 중인 과제는 다음과 같다.

- 개발·테스트 공용 Skill 라이브러리 구축
- 코딩 컨벤션과 Spec 관리 표준화
- Yunxiao에서 결함을 가져와 AI로 수정하고, 자동 회귀 테스트를 돌린 뒤 사람이 검토하는 전체 흐름 구축
- 작업량 자동 산정과 요구사항 분류 실험
- 테스트 환경과 브라우저 호환성 지속 개선
- 요구사항 변경을 제때 공유해 불필요한 논의와 재작업 줄이기

조직 개편 계획은 이미 시작됐고, 주간 업데이트로 진행 상황을 점검하고 조율한다. 그렇다고 순탄하리라 보진 않는다. 기존 프로세스의 관성, 역할 간 굳어진 협업 습관, 기술 인프라의 한계, 새 방식을 기존 업무 리듬에 끼워 맞추는 어려움이 기다리고 있다. 회의 한 번이나 규칙 몇 개로 풀릴 문제가 아니어서, 부딪히는 문제를 그때그때 확인하고 방식을 고쳐가며 팀에 맞는 모델을 찾아가야 한다고 필자는 말한다.

> 팀 안의 정보가 계속 엇갈린다면, 아무리 뛰어난 AI라도 잘못된 맥락을 더 효율적으로 실행할 뿐이다.

도구 몇 개를 사거나 API를 연결하고 에이전트 몇 개를 만든다고 AI 중심 엔지니어링 체계가 생기지는 않는다. 기술 역량, 프로세스 표준, 축적된 지식, 조직의 협업 방식이 함께 바뀌어야 한다.

## AI 시대에 가장 귀한 자원은 코딩 능력이 아닐 수도

필자는 처음엔 테스트 업무를 더 자동화하고 싶었을 뿐이었다. 하지만 AI가 요구사항을 이해하고, 화면을 조작하고, 비정상 시나리오를 스스로 탐색하고, 결함을 등록하고, 수정과 회귀 테스트까지 돕게 되자 테스트만이 아니라 소프트웨어 개발 과정 전체를 다시 봐야 한다는 걸 깨달았다.

예전에는 효율 문제를 특정 역할의 역량 부족이나 특정 단계의 속도 탓으로 돌리곤 했다. 코드 작성이 쉬워진 지금, 실제로 개발을 늦추는 건 동기화되지 않은 요구사항, 불분명한 책임, 사람 사이의 과도한 인계일 수 있다.

필자는 AI가 모두를 프로그래머로 만들 거라고도, 소프트웨어 팀에 제품·개발·QA 같은 전문 역할이 필요 없어질 거라고도 보지 않는다. 다만 이 역할들 사이의 불필요한 벽은 점점 사라질 것이라고 본다.

- 테스터는 케이스 실행을 넘어 리스크 탐색, 문제 분석, 품질 개선에 참여한다.
- 개발자는 요구사항을 받아 코드를 쓰는 데 그치지 않고 더 완결된 문제를 책임진다.
- 기획자는 요구사항을 설명하는 데서 나아가 AI로 아이디어를 직접 검증하고 구현한다.

팀의 경쟁력은 몇 명이 몇 개의 작업을 따로 끝내느냐보다, 정확한 정보를 얼마나 빨리 흘려보내고 모두가 AI로 더 완결된 문제를 풀 수 있게 하느냐에 달려 있을지 모른다는 것이 필자의 결론이다.

> **AI는 코딩을 쉽게 만들고 있다. 하지만 소프트웨어 개발을 정말 빠르게 만드는 건, 사람들이 함께 일하는 방식을 다시 설계하려는 의지일지도 모른다.**
