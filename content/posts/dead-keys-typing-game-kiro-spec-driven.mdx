## 개요

*"틀리는 키가 곧 교재가 된다."*

Dead Keys는 [Kiroween 2026 해커톤](https://kiroween.devpost.com/)에 나온 웹 키보드 트레이너입니다. 1980년대 아케이드 타자 게임 방식을 그대로 가져왔고, 여기에 내가 틀린 키를 모두 세는 기능을 더했습니다. 틀린 키는 화면 속 키보드에 히트맵으로 칠해지고, 다음 연습 문제는 그 키를 중심으로 짜입니다.

만든 사람은 미국 캘리포니아 카운티 법원에서 법원 운영을 맡고 있는 Earl Grey입니다. 2025년 7월부터 AI로 개발을 시작했다고 합니다. 앱은 AWS의 AI 개발 도구 [Kiro](https://kiro.dev)가 스펙 우선 방식으로 만들었습니다. 사흘 동안 약 35시간을 들였고, 스펙 19개와 훅, 커스텀 에이전트 2개, MCP 서버 1개가 들어갔으며 테스트 950개가 통과했습니다.

## 왜 타자 게임인가

작성자는 중학교 때 타자기로 타자를 배웠고, 실력이 붙은 건 집에 있던 Mac의 타자 게임 덕분이었다고 말합니다. 단어가 날아오면 제시간에 치든가 못 치든가, 둘 중 하나였습니다. 배울 건 그게 전부였는데 효과가 있었습니다.

미국 국립교육통계센터(NCES)의 [고교 졸업생 이수 과목 통계](https://nces.ed.gov/nationsreportcard/hsts/2019_tables/2019_table1.aspx)를 보면 타자 수업은 거의 사라졌습니다.

| 연도 | 키보딩 학점을 딴 졸업생 비율 |
|---|---|
| 2000 | 44.1% |
| 2019 | 2.5% |

수업은 사라졌어도 키보드는 그대로 남아 있습니다. 마침 Kiroween에는 "좋아하던 죽은 기술을 되살려라"라는 Resurrection 부문이 있었고, 작성자는 여기에 타자 게임을 들고 나왔습니다.

## AI는 어디까지 맡는가

Dead Keys에는 켜고 끌 수 있는 AI 기능이 있습니다. [Amazon Bedrock의 Nova Micro](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-micro.html)가 내가 자주 틀리는 키를 겨냥한 연습 문장을 써 줍니다. 기본값은 꺼짐이고, 꺼 둬도 게임은 모두 즐길 수 있습니다.

![드릴 라운드 화면. 상단에 'DRILL: BUILT-IN' 라벨이 있고, 'accounts'가 'ac'까지 입력된 상태이며, 드릴에는 목숨과 시간 제한이 없다는 안내가 있다.](https://raw.githubusercontent.com/earlgreyhot1701D/dead-keys/main/docs/screens/post/drill.png)
*모든 드릴에는 누가 만들었는지 표시됩니다. 이건 내장 드릴입니다.*

역할은 분명하게 나눴습니다. 어떤 키가 약한지는 모델이 아니라 코드가 틀린 횟수로 판단합니다. 모델이 보낸 문장도 코드가 하나하나 검사합니다. 글자 구성이 맞는지, 길이가 맞는지, 모든 단어가 사전 목록에 있는 실제 영어 단어인지 확인합니다. 모델 응답이 시간을 넘기거나, 하루 한도를 넘었거나, 이상한 결과를 보내면 내장 드릴로 대신합니다. 지금 받은 드릴이 어느 쪽인지는 화면에 항상 표시됩니다.

## Kiro로 스펙부터 만들기

엔진, 저장소, 첫 화면들, 게임 플레이, 드릴, MCP 서버까지 핵심 부분은 Kiro가 스펙을 보고 만들었습니다. 커밋과 푸시, 배포도 Kiro가 자기 터미널에서 직접 했습니다. 스펙 작성과 각 블록 리뷰는 Claude(Opus 5.5)가 맡았고, Kiro 크레딧을 아끼려고 후반 기능 일부도 Claude가 만들었습니다.

작성자가 Kiro에서 가장 좋아하는 건 스펙 주도 개발(spec-driven development)입니다. 블록마다 요구사항 파일을 먼저 쓰고, 그다음 설계, 그다음 작업 목록을 씁니다. 작업 하나에 파일 하나입니다. 덕분에 지금 어디까지 왔는지를 작성자도 에이전트도 항상 알 수 있었다고 합니다.

![터미널 스타일 패널 'Specs, hooks, steering // .kiro/'. .kiro 폴더 파일 목록 옆에 스펙 19개, 요구사항 279줄, 완료 작업 165개, 훅 5개, steering 파일 5개, 에이전트 2개라는 수치가 있다.](https://raw.githubusercontent.com/earlgreyhot1701D/dead-keys/main/docs/screens/post/kiro-folder.png)
*.kiro 폴더를 저장소에서 그대로 센 결과입니다.*

데모를 녹화한 날 저장소에서 센 숫자는 이렇습니다.

| 항목 | 수치 |
|---|---|
| 스펙 | 19 |
| 요구사항 줄 수 (WHEN ... SHALL) | 279 |
| 완료한 작업 | 165 |
| 훅 (사용 중 4, 폐기 1) | 5 |
| 통과한 단위·속성 테스트 | 949 |
| axe 접근성 검사 | 15회, 이슈 0건 |

### "추측하지 말고 표시하라"

첫 블록에서 Kiro는 데이터 구조를 정의했습니다. 나머지 코드가 모두 기대는 계약입니다. 스펙에는 모르는 건 지어내지 말고 멈춰서 물어보라고 적어 뒀습니다. Kiro는 빈틈 열 개를 들고 돌아왔습니다. 타임스탬프 형식은 무엇인지, 스키마 버전 0인 예전 저장 데이터도 불러올 수 있어야 하는지, 누가 고스트를 백 개씩 저장해서 브라우저 저장 공간을 채우면 어떻게 막는지, 약한 키가 없을 때도 AI를 불러야 하는지 같은 질문이었습니다.

작은 질문 열 개에 답하는 데 5분쯤 걸렸고, 나중에 다시 손볼 일은 없었습니다. 작성자는 스펙이 없었어도 이 질문들은 결국 나왔을 텐데, 그때는 버그의 모습으로 늦게 나왔을 거라고 말합니다.

### 한 번도 실행되지 않은 훅

훅은 특정 이벤트가 생기면 저절로 실행됩니다. 그중 line-cap 훅은 모든 소스 파일을 150줄 아래로 묶어 두어 파일 하나가 비대해지지 않게 막는 역할이었고, 작업이 끝날 때마다 돌도록 계획했습니다.

그런데 이 훅은 한 번도 실행되지 않았습니다. 고른 트리거는 Kiro의 작업 실행기가 작업을 끝낼 때 발생하는데, 실제로는 작업 파일을 직접 고쳐서 완료 표시를 하고 있었기 때문에 그 이벤트가 생기지 않았습니다. [Kiro 훅 문서](https://kiro.dev/docs/hooks/)와 트리거 이름을 맞춰 본 뒤 에이전트가 한 턴을 끝낼 때 실행되도록 바꿨습니다. 실행될 때마다 타임스탬프를 하나씩 남기는 임시 마커를 넣었고, 작성자가 패널에서 "Run Command Hook line-cap"을 직접 확인한 다음 마커를 뺐습니다.

이 일 뒤로는 실제로 실행되는 걸 눈으로 보기 전까지 훅을 있는 것으로 치지 않기로 했습니다. 같은 날 린터가 설정 파일 없이 기본값으로 저장소 전체를 돌고 있었다는 사실도 발견했습니다. 아무도 설정 파일을 쓰지 않았던 겁니다. 에러 47개는 그날 다 고쳤습니다.

### 예제 테스트가 놓친 걸 속성 테스트가 잡다

[속성 기반 테스트](https://fast-check.dev/)는 손으로 고른 예제 몇 개 대신 자동 생성한 입력 수백 개를 함수에 넣어 봅니다. 엔진에서 이 테스트가 버그 하나를 찾았습니다. 시간이 아주 짧으면 나눗셈 중간 단계가 0으로 언더플로되면서 분당 단어 수(WPM) 계산이 NaN을 돌려줬습니다. 그렇게 짧은 시간을 쓴 예제 테스트는 하나도 없었습니다. Kiro가 계산 순서를 바꾸자 테스트가 통과했습니다.

속성 테스트가 정말 실패할 수 있는지 보려고 일부러 규칙을 깨 보기도 했습니다. 테스트는 반례를 내놓으며 실패했고, 규칙은 다시 원래대로 돌려놓았습니다.

### 게임 자체 검사용 MCP 서버

15번째 블록에서 Kiro는 저장소 전용 [MCP](https://modelcontextprotocol.io) 서버를 만들었습니다. 도구는 두 개입니다. 하나는 단어 팩을 검증합니다. 영어 1,500개, 스페인어 1,421개 항목 모두 통과했습니다. 다른 하나는 AI의 골든 테스트 세트를 돌리는데, 비용이 드는 작업이라 `confirm: true`를 넘겨야만 실행됩니다. 단어 팩 폴더 바깥 경로는 거부하고, 비밀 값이나 드릴 텍스트가 응답에 섞이지 않는지도 테스트로 확인합니다.

## 첫 실수는 사람 쪽에 있었다

6번째 블록에서 처음으로 실제 화면을 만들었습니다. 리뷰어 둘 다 불합격을 권했습니다. 타이틀 화면 키보드 버그가 있었고 접근성과 테스트에도 빈 곳이 있었습니다. 작성자도 불합격 처리했지만, 정말 큰 문제는 어떤 검사도 잡지 못했습니다. 화면이 확정해 둔 디자인과 달랐던 겁니다.

Kiro가 잘못한 건 아니었습니다. 스펙에는 디자인 목업이 "참고 자료(reference)"로만 적혀 있었고, 목업과 똑같이 만들라는 작업은 없었습니다. 그래서 Kiro는 더 단순한 버전을 만들었고, 그 차이를 재는 검사도 없었습니다. 빈틈은 Claude가 쓴 스펙에 있었습니다.

작성자가 이런 일을 겪은 건 두 번째입니다. 지난달 [한 사람을 위해 만든 인보이스 앱](https://dev.to/earlgreyhot1701d/an-app-built-for-one-why-a-devpost-skill-pack-made-me-spec-it-anyway-knh)에서는 슬라이스 8개와 E2E 테스트가 모두 통과했는데 계획 자체가 틀려 있었습니다. 직접 앱을 써 보고 나서야 알았습니다. 두 번을 겪고 나서 작성자가 내린 결론은 단순합니다. 검사를 통과했다면 코드가 계획대로라는 뜻이지, 계획이 옳다는 뜻은 아닙니다.

그래서 이번에는 검사 자체를 고쳤습니다. 화면마다 스크린샷을 목업과 나란히 놓고 비교해서 작성자가 직접 승인해야 통과합니다. 데모 영상에 나오는 화면은 이렇게 다시 만든 것들입니다.

## 그 밖에 예상하지 못한 일 두 가지

**첫 배포가 바로 프로덕션으로 나갔습니다.** Kiro의 터미널에서 처음 배포했을 때, 새 프로젝트에서는 [Vercel CLI](https://vercel.com/docs/cli)가 production 플래그 없이도 첫 배포를 프로덕션으로 처리했습니다. 비밀 정보가 들어 있지 않아서 사이트는 그대로 두었습니다. 지금은 배포할 때마다 빌드 검사를 먼저 돌리고, 따로 지시하지 않으면 프리뷰로만 배포합니다.

**AWS 액세스 키가 하나도 없습니다.** 함수는 [Vercel의 OIDC 연동](https://vercel.com/docs/oidc/aws)으로 드릴 라우트 전용 AWS 역할을 맡아서 씁니다. 그러니 유출될 키 자체가 없습니다. AI 드릴의 하루 사용 한도는 코드에 박아 뒀습니다. 예산 알림은 돈을 다 쓴 다음에야 오기 때문입니다.

## 직접 만든 검사 도구로 다시 확인하다

작성자는 무언가를 검사하는 도구를 만드는 사람이라, 제출 직전에 자기 도구 두 개를 Dead Keys에 돌려 봤습니다.

[Agentis Lux](https://agentislux.io)는 원본 페이지를 가져가는 AI 에이전트 눈에 사이트가 어떻게 읽히는지 검사합니다. Dead Keys는 100점 만점에 97점이었습니다. 지적받은 건 두 가지였습니다. 페이지 상단에 본문 바로가기(skip-to-content) 링크가 없었는데, 이건 키보드 사용자도 불편해하는 부분입니다. 그리고 외부 링크 두 개에 `rel` 속성이 빠져 있었습니다.

[README Clew 2](https://readme-clew-2.vercel.app)는 README의 주장을 코드와 대조합니다. 커밋 `fd6bd7c` 기준으로 코드와 어긋나는 주장은 없었습니다. 6개는 검증됐고, 73개는 타자기 추억담처럼 코드로 확인할 수 없는 종류였습니다. 타당한 지적도 하나 있었습니다. 코드는 쓰는데 README에는 이름이 없는 의존성이 6개였고, MCP SDK와 AWS SDK도 거기에 들어 있었습니다.

셋 다 게임을 망가뜨리는 문제는 아니어서 v2 목록에 올렸습니다.

## 아직 안 되는 것

- 물리 키보드가 있어야 하고, 지금은 QWERTY 배열만 지원합니다.
- 게임 플레이는 화면을 봐야 합니다. 메뉴, 레슨, 결과, 진행 화면은 스크린 리더로 쓸 수 있고, 시간 제한 없는 연습 모드를 접근성 대안으로 제공합니다.
- 서버 인스턴스마다 따로 세기 때문에 AI 사용 한도는 대략적인 값입니다.
- 글자 단축키가 아직 없습니다. 메뉴에서는 방향키, Enter, Escape가 작동하지만 Kiro 디스코드의 한 테스터는 이걸 찾지 못했습니다. 그 테스터는 P로 Play를 누르는 식의 글자 단축키와 소리를 더 빨리 켜고 끄는 방법을 제안했고, 두 가지 모두 [v2 목록](https://github.com/earlgreyhot1701D/dead-keys/blob/main/docs/v2.md)에 올라 있습니다.
