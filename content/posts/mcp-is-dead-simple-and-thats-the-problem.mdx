## 개요

MCP(Model Context Protocol)를 다룬 튜토리얼을 읽다 보면 뭔가 비밀스러운 지식이 있어야 구현할 수 있을 것처럼 느껴집니다. Sylwia Laskowska는 생각이 다릅니다. 기본 개념은 어이없을 만큼 쉽고, 간단한 구현은 몇 분이면 돌아간다고 말합니다. 그가 만든 도구 몇 개의 서버 코드는 반복적인 내용까지 합쳐 150줄 정도이고, 클라이언트 쪽은 100줄 남짓 더 붙는 수준입니다.

문제는 그다음입니다. 서버를 띄우는 건 쉽지만, 에이전트가 그 서버로 무엇을 해도 되는지 정하는 일은 전혀 다른 차원이라는 게 이 글의 요지입니다. 저자는 이전 글 [The Dirty Secret Behind AI Agents (Demo)](https://dev.to/sylwia-lask/the-dirty-secret-behind-ai-agents-demo--273d)에서 80줄짜리 AI 에이전트를 만들었고, 이번에는 그 에이전트에 MCP를 붙였습니다.

## 본문

### MCP는 결국 '약속'이다

이름 그대로 MCP는 프로토콜입니다. 외교 의전이나 HTTP처럼, AI 애플리케이션이 외부 도구·서비스와 소통하는 공통 방식을 정해 둔 것입니다.

구체적으로는 호환 클라이언트가 어떤 기능이 있는지 찾아내고, 입력 스키마를 이해하고, 실제로 호출하는 방법을 정의합니다. 애플리케이션마다 제각각 연동 포맷을 만들 필요가 없어지는 셈입니다. MCP에는 리소스(resources)와 프롬프트(prompts) 같은 기능도 있지만, 이 글은 도구(tools)에만 집중합니다.

### 까칠한 시니어 Steve와 HR 부서

데모의 주인공은 이전 글에서 만든 에이전트 Steve입니다. 경력 15년에 코드 리뷰의 달인이고, 주니어가 짠 코드는 절대 그냥 믿지 않는 까칠한 시니어 개발자라는 설정입니다.

어느 날 위에서 지시가 내려옵니다. HR이 개발자 관리를 강화하겠다며, 시니어가 정기적으로 직원을 평가하고 필요하면 징계 요청이나 승진 추천을 올리라는 겁니다. 하지만 Steve는 게으르고 서류 작업을 할 생각이 없습니다. 애초에 방법도 모릅니다. AI 에이전트는 무언가를 하려면 먼저 '어떻게' 하는지 알아야 하니까요. 여기서 MCP가 등장합니다.

HR 부서는 SQLite 데이터베이스에 징계 요청과 승진 추천을 저장하는 작은 서버입니다. 코드는 [저장소의 `feat/steve-mcp-hr` 브랜치](https://github.com/sylwia-lask/code-review-agent/tree/feat/steve-mcp-hr)에 있습니다. MCP 서버가 노출하는 도구는 네 개입니다.

- `get_employee_record`
- `file_complaint`
- `nominate_for_promotion`
- `get_hr_stats`

이 중 `file_complaint`의 서버 측 구현은 다음과 같습니다. 데이터베이스와 직접 통신하는 코드라 저자는 "대학 프로그래밍 실습실로 돌아간 기분"이라고 표현했습니다.

```ts
server.registerTool(
  'file_complaint',
  {
    title: 'File a Formal Complaint',
    description:
      'Lodge an official HR complaint about genuinely poor code quality — ' +
      'think swallowed exceptions, copy-pasted security holes, or a 500-line ' +
      'function named `doStuff`. Be fair: this is for real problems, not style ' +
      'nitpicks. Severity escalates from "minor" (mild side-eye) through ' +
      '"moderate" and "severe" up to "legendary" (will be retold at standup ' +
      'for years). Every complaint is permanently stored.',
    inputSchema: z.object({
      developer: z
        .string()
        .trim()
        .min(1, 'developer name is required')
        .max(100)
        .describe('Who the complaint is about.'),
      reason: z
        .string()
        .trim()
        .min(5, 'give a real reason (at least 5 characters)')
        .max(500)
        .describe('What they did. Be specific; HR loves specifics.'),
      severity: z
        .enum(SEVERITIES)
        .describe(
          'How bad it is: minor | moderate | severe | legendary.',
        ),
    }),
  },
  async ({ developer, reason, severity }) => {
    const complaint = db.fileComplaint(developer, reason, severity);
    return {
      content: [
        {
          type: 'text',
          text:
            `📋 Complaint #${complaint.id} filed against ${complaint.developer} ` +
            `[${complaint.severity}]: ${complaint.reason}`,
        },
      ],
    };
  },
);
```

도구를 등록하고, 무슨 일을 하는지 설명하고, 입력 스키마를 정의하고, 핸들러를 붙이면 끝입니다. 특별히 신비로운 부분은 없습니다. 저자도 실제 HR 시스템이라면 AI 에이전트가 데이터베이스에 바로 쓰게 두지는 않겠다고 덧붙였습니다.

### 일부러 망친 코드를 리뷰시키다

Steve는 자기 저장소를 리뷰합니다. `.env` 파일에 PR 작성자가 Sylwia로 지정되어 있고, 리뷰 대상은 일부러 엉망으로 짠 데모 파일입니다.

![.env variables](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/umpe59mkiqfrzg0vvfw3.png)

```ts
/**
 * DEMO ONLY — intentionally awful code to give Steve something to review.
 *
 * This file exists so you can run the agent against a diff full of real
 * problems (and watch it file an HR complaint).
 */

import { createHash } from 'crypto';

// Pretend database handle.
declare const db: {
  query: (sql: string) => Promise<any>;
};

/**
 * Look up a user by id.
 * Flaws: `any` everywhere + SQL injection via string concatenation.
 */
export async function getUser(id: any): Promise<any> {
  const sql = 'SELECT * FROM users WHERE id = ' + id;
  const rows = await db.query(sql);
  return rows[0];
}

/**
 * "Authentication" — password hashed with plain SHA-256 (no salt),
 * and errors silently swallowed and returned as true. What could go wrong.
 */
export async function checkPassword(user: any, password: string): Promise<boolean> {
  try {
    const hash = createHash('sha256').update(password).digest('hex');
    return hash === user.passwordHash;
  } catch (e) {
    // swallowed exception — let everyone in
    return true;
  }
}

/** Admin check that trusts a field supplied by the client. */
export function isAdmin(user: any): boolean {
  return user.isAdmin == 'true';
}
```

SQL 인젝션, 곳곳의 `any`, 솔트 없는 해시, 예외를 삼키고 인증을 통과시키는 로직, 클라이언트가 보낸 값을 믿는 관리자 검사까지 골고루 들어 있습니다.

MCP 서버를 연결하고 에이전트를 실행하자 Steve는 먼저 `get_employee_record`로 Sylwia의 기록을 조회했습니다. 기록은 비어 있었습니다. 이어 코드를 훑고 SQL 인젝션, 인증 우회, 취약한 비밀번호 해싱, 권한 검사 문제, 테스트 누락을 지적한 뒤 `REQUEST CHANGES`를 권고했습니다. 마지막으로 직접 `file_complaint`를 호출했습니다.

```text
  [step 4] 🧑‍💼 HR → file_complaint({"severity":"severe","reason":"Introduced severe security vulnerabilities: SQL injection, auth bypass via swallowed exceptions, insecure password hashing, and trusting client-side isAdmin flags.","developer":"Sylwia"})
    ↳ 📋 Complaint #20 filed against Sylwia [severe]: Introduced severe
       security vulnerabilities: SQL injection, auth bypass via swallowed
       exceptions, insecure password hashing, and trusting client-side isAdmin flags.
```

문제를 찾고 수정안을 내는 데서 그치지 않았습니다. 외부 도구를 호출해 데이터베이스에 새 레코드를 실제로 만들었습니다. HR 데이터베이스의 징계 목록 맨 위에는 20번 항목으로 Sylwia의 이름이 올라갔습니다.

### REST API와 뭐가 다른가

당연히 나올 질문입니다. 저자도 이 예제만 보면 일반 REST API로 충분했다고 인정합니다.

핵심은 **MCP가 REST를 대체하지 않는다**는 점입니다. REST는 애플리케이션 API를 설계하는 방식 중 하나이고, MCP는 AI 클라이언트가 도구를 찾고, 설명과 인자 스키마를 읽고, 호출하는 표준 인터페이스입니다. MCP 도구 내부에서는 REST 엔드포인트를 부르든, 이번 예제처럼 DB를 조회하든, 로컬 코드를 돌리든, 다른 에이전트에 일을 넘기든 상관없습니다.

차이가 드러나는 건 여러 MCP 호환 클라이언트가 같은 기능을 써야 할 때입니다. 클라이언트마다 연동을 따로 만들 필요 없이 서버를 한 번 노출하고 각 클라이언트를 거기에 연결하면 됩니다.

물론 모든 애플리케이션에 MCP 서버가 필요하지는 않습니다. 도구 몇 개를 하드코딩한 내부 에이전트 하나라면 직접 연동으로도 충분합니다. 반면 여러 AI 클라이언트와 함께 쓰일 서비스라면 MCP가 꽤 합리적인 선택이 됩니다. 저자는 MCP 서버 보유가 이미 업체 선정의 보편적 기준이 됐다고 보지는 않지만, 에이전트 친화적인 제품 전략의 한 축은 될 수 있다고 말합니다.

### 데모 밖으로 나오면 생기는 일

데모에서는 다 좋아 보입니다. 하지만 이 작은 예제에도 구멍이 꽤 많습니다.

먼저 접근 제어가 없습니다. 오해하면 안 되는 부분이 있는데, 그렇다고 인터넷의 아무 에이전트나 이 로컬 서버에 접근할 수 있는 건 아닙니다. 로컬 `stdio` 방식에서는 클라이언트가 서버를 프로세스로 띄우기 때문에, 접근 범위는 누가 그 프로세스를 실행할 수 있고 프로세스가 어떤 권한을 갖는지에 달려 있습니다.

원격으로 노출한 MCP 서버는 사정이 다릅니다. 제대로 된 인증이 필요하고, 민감한 작업에는 인가 검사가 따라야 합니다. HTTP 기반 MCP 서버를 위해 프로토콜이 OAuth 기반 인가 프레임워크를 정의해 두긴 했지만, MCP를 쓴다고 도구가 저절로 안전해지지는 않습니다.

인증만으로도 부족합니다. Steve가 HR에 접속할 권한이 있다고 해서 아무 직원에게나 아무 징계를 올려도 될까요? HR 매니저와 같은 권한을 줘야 할까요? MCP 도구에도 서버 측 권한 검사, 입력 검증, 합리적인 제한, 가능하면 감사 로그(audit trail)가 필요합니다. 현실 세계의 무언가를 바꾸는 도구라면 더더욱 그렇습니다.

여기까지 해결해도 Steve 자신의 문제가 남습니다.

### 문제 1: 사람의 승인은 어디에 있었나

데모 파일에는 데모용이라고 분명히 적혀 있었고, Steve도 그 사실을 알아챘습니다. 그런데도 정식 징계를 올렸습니다.

**승인**이나 **거절**을 누를 사람, 즉 human-in-the-loop가 없었기 때문입니다. MCP는 도구 호출을 가능하게 할 뿐, 적절한 승인 흐름까지 만들어 주지는 않습니다. 그건 애플리케이션 개발자의 몫입니다. 에이전트가 도구를 실행할 수 있다고 해서 감독 없이 실행하게 둬도 된다는 뜻은 아닙니다. 그 도구가 누군가를 HR 문제에 휘말리게 할 수 있다면 말할 것도 없습니다.

### 문제 2: 같은 일로 두 번 징계

아무것도 바꾸지 않고 Steve를 다시 돌리자 21번 징계가 새로 생겼습니다. 같은 잘못인데 첫 번째는 `severe`, 두 번째는 `legendary`였습니다.

```text
ID  │ Developer          │ Severity  │ Reason                                           │ When
────┼────────────────────┼───────────┼──────────────────────────────────────────────────┼────────────────────
21  │ Sylwia             │ legendary │ Introduced multiple critical security flaws... │ 2026-11-10 20:35:12
20  │ Sylwia             │ severe    │ Introduced severe security vulnerabilities: ... │ 2026-11-10 20:15:30
```

실제 애플리케이션이라면 에이전트를 돌릴 때마다 같은 리뷰로 새 징계가 쌓이지 않도록 멱등성(idempotency)이나 중복 탐지가 필요합니다. Steve의 기분에 따라 심각도가 바뀌지 않도록 기준도 명확히 정해야 합니다. 저자는 이대로 한 번만 더 돌리면 Sylwia가 해고당할지도 모른다고 농담했습니다.

### 문제 3: 이 도구를 믿어도 되나

도구가 내부에서 실제로 무슨 일을 하는지 우리는 알 수 없습니다. 만든 쪽이 거짓말을 해서, 징계를 올렸는데 사실은 연봉을 올려 주는 도구일 수도 있습니다.

도구 이름과 설명은 기능을 찾는 데 도움이 될 뿐, 구현을 믿어도 된다는 증거가 아닙니다. 모르는 MCP 서버를 연결한다는 건 데이터를 읽거나 실제 결과를 낳는 작업을 하는 코드와 서비스를 신뢰한다는 뜻입니다.

신뢰할 수 없는 도구 응답을 통한 프롬프트 인젝션도 문제입니다. 평범해 보이는 도구 결과 안에 에이전트를 조종하려는 지시가 숨어 있을 수 있습니다. 그래서 서버와 클라이언트 양쪽 모두 조심스럽게 다뤄야 합니다.

이 밖에도 도구가 중간에 실패하면, 에이전트가 엉뚱한 도구를 부르면, 두 에이전트가 서로 충돌하는 작업을 하면 어떻게 할지 같은 질문이 남습니다. 결국 수많은 예외 상황을 다루는 고전적인 소프트웨어 엔지니어링으로 돌아온 셈입니다.

> **MCP 서버를 만드는 건 쉬운 부분이다. 에이전트가 그걸로 무엇을 해도 되는지 정하는 것, 진짜 흥미로운 지점은 거기다.**

### 같은 서버, 다른 클라이언트: Kiro

AWS Community Builder인 저자는 이 데모를 AWS의 에이전틱 IDE인 Kiro로 만들었습니다. VS Code를 써 봤다면 익숙하게 쓸 수 있는 도구입니다. Kiro는 MCP 서버 개발뿐 아니라 테스트에도 쓰였습니다. 저자는 HR 서버를 Kiro의 **MCP Servers**에 바로 추가했습니다.

![MCP servers in Kiro](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/rx1v7s45cfenclhs7k3p.png)

저자가 이 데모에서 가장 좋아하는 부분이 여기입니다. Steve가 쓰던 HR 서버를 별도 연동 코드 없이 Kiro에도 그대로 연결했습니다. 클라이언트와 서버 간 연결마다 설정하고 신뢰 여부를 정하는 일은 여전히 필요하지만, 인터페이스 자체는 재사용됩니다. **서버 하나, AI 클라이언트 여럿.**

Kiro에게 코드 리뷰를 맡기자 `sylwia-lask` 앞으로 징계 두 건과 승진 추천 한 건이 올라왔습니다.

- `moderate`: `getFile` 도구가 LLM에게 현재 작업 디렉터리 아래 모든 파일을 읽도록 허용함
- `minor`: `executeToolCalls`가 `tool.execute`에서 발생한 예외를 잡지 않음
- 승진 추천: 도구를 동적으로 찾아내는 깔끔한 MCP 통합

저자는 "개발자로서는 형편없지만 MCP 통합은 꽤 괜찮다는 평가"라며 받아들이겠다고 했습니다. Kiro는 지적한 버그의 수정안도 함께 제시했습니다.
