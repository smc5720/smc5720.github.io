## 개요

개발자 Jessica Doering은 처음엔 터미널에 별 관심이 없었습니다. 디렉터리를 옮겨 다니고, 패키지를 설치하고, 개발 서버를 띄우고, Git 명령 몇 개 치는 정도였죠. 대부분 버튼 몇 번 누르면 되는 일이었고, 그게 이상하다고 느끼지도 않았습니다. "할 수 있으니까 뭐든 터미널로 하는 사람"이 될 생각도 없었다고 합니다.

그런데 개발 경험이 쌓이고, 특히 Linux를 오래 쓰면서 터미널을 여는 일이 늘었습니다. 더 빨라서일 때도 있었고, 마땅한 GUI가 없어서일 때도 있었습니다. 따라 치는 명령어의 절반은 뭘 하는지도 모르는 채로 실행하던 때도 있었고요. 그러다 바로 그 부분이 궁금해지기 시작했습니다. 이 명령은 실제로 뭘 하는 걸까? 왜 되고, 왜 안 될까? 애초에 이걸 왜 실행하고 있지?

저자는 그 과정에서 명령어 사용법보다 훨씬 큰 걸 얻었다고 말합니다. 익숙한 인터페이스 아래에서 무슨 일이 벌어지는지 이해하게 된 겁니다. 그리고 이게 명령어를 빨리 치는 능력보다 훨씬 쓸모 있었다고요.

## 터미널이 보여준 것들

### 파일시스템: "지금 어디 있는지"가 중요해졌다

파일과 폴더 자체는 누구나 압니다. 파일 탐색기에서 몇 년씩 이리저리 옮겨 왔으니까요. 하지만 터미널에서는 평소 그냥 넘겼던 것들이 눈에 들어옵니다.

```bash
pwd
ls -la
cd ..
```

특별할 것 없는 명령이지만, 터미널에서는 현재 위치가 실제로 결과를 좌우합니다. 저자는 엉뚱한 디렉터리에서 뭔가를 실행했다가 낭패를 본 일이 셀 수 없이 많았다고 합니다. 설정 파일이 안 보여서 헤매다가 숨김 파일이라는 걸 뒤늦게 떠올린 적도 있고, 상대 경로를 쓰면서 그게 *어디 기준*인지 생각하지 않아 실패한 적도 있습니다.

폴더를 클릭으로 오갈 때는 몰라도 넘어갈 수 있던 것들입니다. 터미널을 쓰면서 숨김 파일, 심볼릭 링크, 절대 경로와 상대 경로의 차이, 애플리케이션이 설정 파일을 두는 위치에 신경 쓰게 됐고, 헷갈리던 자잘한 문제들이 하나씩 이해되기 시작했습니다. 저자는 터미널이 자신을 갑자기 똑똑하게 만든 게 아니라고 강조합니다. 인터페이스에 맡기던 일을 직접 이해해야 했을 뿐이라는 거죠.

### 프로세스: "실행 중"이 무슨 뜻인지 알게 됐다

저자에게 가장 크게 다가온 부분입니다. 보통 애플리케이션은 아이콘을 누르면 열리고, 다 쓰면 닫으면 끝입니다. 그 뒤에서 벌어지는 일은 크게 신경 쓸 필요가 없었죠.

터미널에서 프로그램을 돌리면 프로세스가 훨씬 잘 보입니다. 웹 앱을 만들 때 특히 그렇습니다. Vite로 개발해 본 사람이라면 "포트가 이미 사용 중"이라는 메시지를 한 번쯤 봤을 겁니다. 서버를 띄우려는데 누군가 이미 그 포트를 차지하고 있는 상황이죠. 범인은 깜빡하고 안 끈 내 앱의 다른 인스턴스일 때가 많습니다. 저자도 겪어봐서 안다고 덧붙입니다.

저자는 아무 터미널 창이나 닫고 잘되길 비는 대신, 실제로 뭐가 돌고 있는지 확인하는 법을 익혔습니다.

```bash
ps aux
pgrep -af node
ss -ltnp
```

5173번 포트를 누가 점유하고 있는지만 보고 싶다면 이렇게 합니다.

```bash
ss -ltnp | grep ':5173'
```

이 명령들로 시스템의 프로세스와 리스닝 소켓을 살펴볼 수 있습니다. 권한에 따라 소켓에 연결된 프로세스가 전부 보이지 않을 수도 있지만, 출발점으로는 충분합니다.

사소해 보여도 효과는 컸습니다. 실행 중인 애플리케이션과 그 프로세스, 그리고 사용하는 포트가 어떻게 연결되는지 이해하자 다른 개념들도 덩달아 정리됐습니다. 예전에는 브라우저에 앱이 뜨면 서버가 돌고 있다고 알았을 뿐인데, 이제는 *실행 중*이라는 말이 실제로 무슨 뜻인지 감이 생겼다고 합니다.

### 권한: sudo부터 붙이기 전에

읽기, 쓰기, 실행. Linux 권한은 이론으로는 아는 내용이었습니다. 그런데도 파일을 수정하지 못하거나 스크립트가 실행되지 않으면 도대체 왜 이러나 싶었다고 합니다. 제대로 안다고 할 수는 없었던 셈이죠.

터미널에서는 무슨 일이 벌어지는지 직접 들여다볼 수 있습니다.

```bash
ls -l script.sh
stat script.sh
```

Permission denied 메시지에 짜증만 내는 대신 파일 소유자와 권한을 확인하게 됐습니다. 왜 어떤 파일은 읽을 수는 있는데 쓸 수는 없는지, 스크립트가 버젓이 있는데 왜 실행이 안 되는지 이해하기 시작했죠. 디렉터리의 실행 권한은 파일의 실행 권한과 뜻이 조금 다르다는 것도 알게 됐습니다. 디렉터리에서는 그 안으로 들어갈 수 있는지(traverse)를 뜻합니다. 이해하기 전까진 이상해 보이는 Linux의 디테일 중 하나입니다.

`sudo`도 있습니다. Linux를 배우는 단계에서는 권한 오류가 나면 일단 앞에 sudo를 붙이고 싶어집니다. 문제 해결! 일까요? 명령은 돌아가겠지만 왜 관리자 권한이 필요했는지는 여전히 모릅니다. 상황에 따라서는 root 소유가 되면 안 되는 파일을 root 소유로 만들어 버릴 수도 있습니다.

저자는 "어떻게든 돌아가게 만드는 것"과 "왜 안 됐는지 이해하는 것"이 전혀 다른 일이라는 걸 배웠고, 이 교훈이 개발 전반에서 자주 떠오른다고 말합니다.

### 네트워크: 어디서부터 볼지 알게 됐다

DNS가 뭔지, 포트가 뭔지, 애플리케이션이 네트워크로 통신한다는 것도 알았습니다. 하지만 막상 연결이 안 되면 그 지식만으로는 어디서부터 봐야 할지 알 수 없었습니다. 호스트 이름은 제대로 해석되나? 서버는 응답을 하나? 내 앱은 내가 생각한 포트에서 리스닝하고 있나? 아니면 전혀 상관없는 데를 망가뜨린 건가?

터미널은 범위를 좁혀 나갈 수단이 됐습니다.

```bash
dig example.com
curl -I https://example.com
ss -ltn
```

명령마다 보는 곳이 다릅니다.

- `dig`: DNS 해석 확인
- `curl`: HTTP 요청을 보내고 응답 확인
- `ss`: 내 시스템에서 리스닝 중인 TCP 포트 확인

물론 이 명령들이 모든 네트워크 문제를 풀어 주지는 않습니다. 그래도 시작할 지점은 생깁니다. 저자는 연결 실패를 하나의 거대한 미스터리로 보지 않고, 어느 부분이 실패했는지 따지게 된 것이 가장 큰 변화였다고 합니다. "앱이 연결이 안 돼요"는 꽤 여러 가지 뜻일 수 있고, 그중 무엇인지 알면 문제 해결이 훨씬 쉬워집니다.

### 에러 메시지를 제대로 읽게 됐다

우습게 들릴 수 있지만, 저자가 터미널에서 얻은 가장 쓸모 있는 습관은 도구가 하는 말을 *제대로* 읽는 것이었습니다. 에러를 대충 훑고 고장 났다고 판단한 다음, 될 때까지 이것저것 시도하는 게 아니라요.

터미널에서는 출력이 많습니다. 컴파일러 에러, 의존성 경고, 스택 트레이스, 서버 로그, 그리고 작은 실수 하나 때문에 쏟아지는 어마어마한 텍스트까지요. 처음엔 압도되고, 지금도 가끔은 그렇습니다. 하지만 자꾸 보다 보니 어디에 주목해야 하는지 보이기 시작했습니다.

- 환경 변수 누락과 네트워크 요청 실패는 다른 문제다.
- 의존성 충돌은 문법 오류가 아니다.
- 시작하자마자 죽는 앱과, 멀쩡히 돌지만 기대대로 응답하지 않는 앱은 전혀 다른 문제다.

여전히 에러를 보며 이게 무슨 소린가 싶을 때가 있지만, 이제는 해결책을 하나 더 던져 보기보다 실제 에러를 파고들 가능성이 높아졌습니다. 검색할 때도 *무엇을* 찾아야 하는지 훨씬 잘 안다고 합니다.

## 진짜 얻은 것: 조사하는 습관

저자는 쓸 만한 명령어 몇 개 익혀서 작업 속도가 좀 빨라지는 정도를 기대했습니다. 정작 예상하지 못한 변화는 문제를 대하는 방식 자체가 바뀌었다는 점이었습니다.

이제는 뭔가 안 되면 질문부터 던집니다.

- 이 명령은 실제로 어디서 실행되고 있지?
- 저 포트는 어떤 프로세스가 쓰고 있지?
- 이 파일 주인은 누구지?
- 서버가 응답은 하고 있나?
- 에러 메시지가 실제로 뭐라고 하지?

그렇다고 답을 항상 아는 건 아닙니다. 여전히 절반은 명령어를 찾아보고 문서를 읽고, 안다고 생각한 게 예상과 조금 다르게 동작한다는 걸 알게 되는 일의 반복입니다. 저자는 그게 바로 핵심이라고 말합니다. 터미널에 익숙하다는 건 명령어 수백 개를 외우거나 기괴한 원라이너를 기억에서 꺼내 치는 능력이 아니라, 무슨 일이 벌어지는지 조사할 방법이 있다는 걸 알고 그걸 찾아낼 의지가 있다는 뜻이라고요. 아는 명령을 바로 쓰는 것도, 그 명령이 왜 예상대로 안 됐는지 20분 동안 문서를 뒤지는 것도 똑같이 쓸모 있습니다.

## 직접 해볼 만한 연습 다섯 가지

터미널이 아직 낯설거나 패키지 설치와 개발 서버 실행 정도로만 써 왔다면, 저자가 제안하는 아래 연습을 해볼 만합니다. 저자가 Linux를 쓰기 때문에 예시도 Linux 기준이며, macOS나 Windows에서는 명령이 다를 수 있습니다. 명령을 외울 필요는 없습니다. 명령이 보여 주는 정보를 보고, 그게 왜 중요한지 이해하면 됩니다.

### 1. 프로젝트 디렉터리 자세히 보기

프로젝트 폴더에서 터미널을 열고 실행해 봅니다.

```bash
pwd
ls -la
find . -maxdepth 2 -type f
```

지금 위치, 숨김 파일, 파일 구성을 살펴보세요. 다른 디렉터리에서도 실행해 보고 무엇이 달라지는지 비교해 봅니다. 특히 상대 경로에 주목하세요. 단순하지만, 뭔가 안 될 때 원인이 되는 경우가 많습니다.

### 2. 개발 서버 찾아보기

평소처럼 개발 서버를 띄운 뒤, 다른 터미널을 열고 실행합니다.

```bash
pgrep -af node
ss -ltnp
```

Linux에서 Node 기반 개발 서버를 쓰고 있다면 해당 프로세스와 리스닝 포트를 찾아보세요. 기대한 프로세스 정보가 안 보인다면 이유를 찾아봅니다. 권한 문제일 수도 있고, 서버가 다른 실행 파일을 거쳐 돌고 있을 수도 있습니다. 그 조사 자체가 연습입니다.

### 3. 파일 권한 보기

프로젝트 안의 파일 하나를 골라 실행합니다.

```bash
ls -l package.json
stat package.json
```

권한 비트는 각각 무슨 뜻인지, 파일 주인은 누구인지, 소유자는 할 수 있지만 다른 사용자는 못 하는 건 무엇인지 생각해 봅니다. 실험한다고 권한을 바꿀 필요는 없습니다. 저자는 오히려 바꾸기 전에 지금 보이는 게 뭔지부터 이해하라고 권합니다.

### 4. HTTP 요청 들여다보기

```bash
curl -v https://example.com
```

출력에는 연결 정보, TLS 협상 과정, 요청 헤더, 응답 헤더가 담겨 있습니다. 한 번에 다 이해할 필요는 없습니다. 모르는 항목 하나를 골라 찾아보세요. 저자도 실제로 그렇게 많은 걸 배웠다고 합니다.

### 5. 파이프 써 보기

```bash
printf 'apple\nbanana\napricot\n' | grep '^a'
```

결과는 다음과 같습니다.

```text
apple
apricot
```

`|`는 한 명령의 출력을 다른 명령으로 넘깁니다. 단순한 아이디어지만, Unix 계열 커맨드라인 환경을 쓸모 있게 만드는 핵심 중 하나입니다. 모든 걸 하는 거대한 도구 대신 작은 도구들을 이어 붙일 수 있으니까요. 이 개념이 잡히면 여러 터미널 작업 흐름이 이해되기 시작하니, 이 예제 말고도 더 실험해 볼 만합니다.

## 모든 걸 터미널로 할 필요는 없다

저자는 오해가 없도록 선을 긋습니다. GUI 애플리케이션을 버리고 평생 터미널만 보라는 얘기는 아닙니다. 저자도 GUI 앱을 늘 쓰고, 좋은 인터페이스로 하는 게 나은 일도 많습니다. 커맨드라인으로도 할 수 있다는 걸 증명하려고 일을 괜히 복잡하게 만들 생각은 없다고 합니다.

터미널을 쓴다고 자동으로 더 나은 개발자가 되는 것도 아닙니다. 무슨 뜻인지 하나도 모른 채 명령어를 종일 복사해 붙여넣을 수도 있고, GUI도 마찬가지로 아무 이해 없이 클릭만 할 수 있습니다. 저자가 꼽는 차이는 호기심입니다. 명령이 뭘 하는지, 왜 되는지, 왜 가끔 처참하게 실패하는지 관심을 가지면서 훨씬 많이 배우게 됐다는 겁니다. 터미널은 평소 GUI가 대신 처리해 주는 것들을 유난히 잘 보이게 해 줄 뿐입니다.

## 타이핑 속도의 문제가 아니다

몇몇 작업은 확실히 빨라졌습니다. 메뉴를 이리저리 누르는 것보다 터미널에서 명령 한 줄 치는 게 편한 일도 많습니다. 하지만 저자에게 가장 값진 변화는 그게 아니었습니다.

이제 저자에게 애플리케이션은 아이콘을 누르면 열리는 무언가가 아닙니다. 프로세스가 돌고, 파일에 접근하고, 권한을 확인하고, 네트워크 연결을 맺는 일들이 뒤에서 벌어지고 있다는 걸 압니다. 그래서 뭔가 잘못되면 어디부터 봐야 할지 훨씬 잘 알게 됐습니다.

저자는 여전히 배울 게 산더미라고 말합니다. 늘 검색하고, 완전히 이해하지 못한 것도 일단 실험해 보고, 가끔은 너무 자신만만하게 굴다 뭔가를 망가뜨리기도 합니다. 그래도 문제를 풀어 가는 능력은 점점 나아지고 있습니다. 커맨드라인 전문가가 된 게 아니라, 더 나은 조사자가 됐다는 것. 그리고 개발을 알아 갈수록 이게 꽤 중요한 능력이라는 걸 깨닫는다는 말로 글을 맺습니다.
