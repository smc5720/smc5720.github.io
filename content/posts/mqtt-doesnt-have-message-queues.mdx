## 개요

MQTT(Message Queuing Telemetry Transport)라는 이름을 처음 보면 대부분 RabbitMQ 같은 메시지 큐를 떠올립니다. 하지만 MQTT에는 큐가 없습니다. 메시지를 FIFO 큐에 쌓아두지도 않고, Kafka처럼 파티션 로그를 저장하지도 않습니다. 영속 세션 없이 구독자가 오프라인이면 들어온 메시지는 그냥 사라집니다.

작성자 S M Tahosin은 MQTT를 "바이너리로 프레이밍된 초경량 Pub/Sub 이벤트 라우터"라고 정의합니다. 고정 헤더는 최소 **2바이트**면 충분합니다. 이 글에서는 와이어 포맷, QoS 핸드셰이크, 브로커 라우팅, 장애 감지, MQTT v5의 공유 구독까지 MQTT가 내부적으로 어떻게 움직이는지 차례로 살펴봅니다.

## 사막의 송유관에서 시작된 프로토콜

1999년, Andy Stanford-Clark와 Arlen Nipper는 미국 남서부 사막 수백 마일에 걸친 원유 송유관을 원격으로 감시해야 했습니다. 쓸 수 있는 통신 수단은 킬로바이트 단위로 요금이 붙는 불안정한 저대역 위성 링크뿐이었고, 배터리로 돌아가는 센서는 8비트 마이크로컨트롤러에 메모리도 아주 작았습니다.

HTTP를 썼다면 매번 반복되는 텍스트 헤더만으로 하루 수천 달러의 위성 요금이 나가고, 배터리는 일주일도 못 버텼을 겁니다. 두 사람은 이 문제를 풀려고 가벼운 바이너리 프로토콜을 설계했고, 그게 MQTT입니다.

지금 MQTT는 전 세계 수억 대의 기기에서 돌아갑니다.

- 전기차가 클라우드로 보내는 실시간 배터리·GPS 텔레메트리
- Home Assistant, Zigbee 네트워크의 스마트 전구와 센서
- 산업용 로보틱스와 제조 라인의 SCADA 시스템
- 저사양 휴대폰의 배터리를 아끼려고 모바일 푸시 알림을 MQTT로 옮긴 Facebook Messenger

## MQTT에 큐가 없는 이유

RabbitMQ, ActiveMQ, Amazon SQS 같은 큐는 이렇게 움직입니다. 퍼블리셔가 이름 붙은 큐에 작업을 넣으면 큐가 메시지를 보관하고, 컨슈머가 나중에 접속해 꺼내 처리한 뒤 수신을 확인합니다.

MQTT는 패러다임 자체가 다릅니다. 작성자는 이를 **공간·시간·동기화의 분리(Space, Time, and Synchronization Decoupling)**라고 설명합니다.

```plaintext
[ Sensor / Publisher ] ──> PUBLISH "factory/temp" ──> [ MQTT Broker ] ──> Instant Push ──> [ Subscribers ]
                                                              │
                                            (If 0 subscribers are online:
                                             Message is dropped immediately!)
```

![MQTT Publish/Subscribe vs Traditional HTTP Request/Response Architecture](https://iili.io/nMf3I72.png)

### 퍼블리셔와 구독자는 서로를 모른다

`factory/temp`에 온도를 보내는 센서는 어떤 서비스가 있는지, 대시보드가 몇 개 열려 있는지, 그 IP가 뭔지 전혀 모릅니다. EMQX, Mosquitto, HiveMQ 같은 **MQTT 브로커**에 패킷을 보내고 바로 절전 상태로 돌아갈 뿐입니다.

### 메시지는 큐가 아니라 토픽으로 간다

브로커가 `PUBLISH` 패킷을 받으면 다음 순서로 처리합니다.

1. 메모리에 있는 구독 트리를 보고 지금 그 토픽을 듣는 클라이언트를 찾습니다.
2. 구독자가 셋이면 패킷을 복제해 열린 TCP 연결 세 개로 바로 보냅니다.
3. **구독자가 없으면 메시지를 즉시 버립니다.**

기본 저장소도 없고, 내일 켜질 구독자를 기다려주는 큐도 없습니다.

예외는 클라이언트가 **영속 세션(Persistent Session)**으로 접속했을 때입니다. MQTT 3.1.1에서는 `CleanSession=false`, MQTT 5.0에서는 `CleanStart=false`에 `Session Expiry Interval`을 함께 설정합니다. 이 경우 브로커는 해당 `ClientId` 앞으로 온 미확인 QoS 1·2 메시지를 버퍼에 보관합니다. 그래도 토픽 자체는 상태 없는 브로드캐스트 채널일 뿐, 독립된 큐가 되지는 않습니다.

## 2바이트 고정 헤더의 구조

IoT 센서가 코인 배터리 하나로 5년을 버티는 비결은 바이너리 와이어 포맷에 있습니다.

HTTP/1.1로 숫자 하나를 보내려면 수백 바이트짜리 텍스트가 필요합니다.

```http
POST /telemetry HTTP/1.1
Host: api.iot.com
Content-Type: application/json
Content-Length: 18
User-Agent: Mozilla/5.0...

{"temperature":24}
```

MQTT의 고정 헤더는 최소 **2바이트**입니다.

![Anatomy of the 2-Byte Fixed Header Wire Format](https://iili.io/nMf35Xe.png)

### 1번 바이트: 패킷 타입과 제어 플래그

첫 바이트는 비트 단위로 쪼개 씁니다.

```plaintext
Bit:   7   6   5   4  │  3  │  2   1  │   0
     [  Packet Type  ] │ DUP │  [ QoS ] │ RETAIN
```

- **7~4번 비트(패킷 타입):** 4비트로 16가지 제어 패킷을 구분합니다.
  - `0001`(1): `CONNECT` — 클라이언트 연결 요청
  - `0010`(2): `CONNACK` — 브로커의 연결 확인
  - `0011`(3): `PUBLISH` — 메시지 발행
  - `0100`(4): `PUBACK` — QoS 1 발행 확인
  - `1100`(12): `PINGREQ` — 하트비트 요청
  - `1101`(13): `PINGRESP` — 하트비트 응답
  - `1110`(14): `DISCONNECT` — 정상 종료
- **3번 비트(DUP):** 확인받지 못한 QoS 1·2 패킷을 다시 보낼 때 `1`로 설정합니다.
- **2~1번 비트(QoS):** `00`은 QoS 0(최대 한 번), `01`은 QoS 1(최소 한 번), `10`은 QoS 2(정확히 한 번)입니다.
- **0번 비트(RETAIN):** `1`이면 브로커가 이 메시지를 해당 토픽의 '마지막 정상값'으로 저장합니다. 이후 새로 구독하는 클라이언트는 구독 즉시 이 메시지를 받습니다.

### 2번 바이트부터: 가변 길이 필드

작은 센서 값마다 길이 필드에 여러 바이트를 낭비하지 않으려고, MQTT는 **가변 바이트 정수(Variable Byte Integer)**를 씁니다.

- 각 바이트의 하위 **7비트**에 길이 값(0~127)을 담습니다.
- 최상위 비트(MSB)는 **연속 비트**입니다. `0`이면 거기서 끝나고, `1`이면 다음 바이트에 길이가 이어집니다.

덕분에 128바이트 미만 페이로드는 길이 필드가 **1바이트**면 되고, 큰 페이로드는 최대 4바이트까지 늘어나 **268,435,455바이트(256MB)**까지 표현할 수 있습니다.

마이크로컨트롤러가 QoS 0으로 온도 값을 보낼 때 프로토콜 오버헤드는 말 그대로 2바이트입니다.

```hex
0x30 0x12
```

`0x30`은 패킷 타입 3(`PUBLISH`), QoS 0, retain 없음이라는 뜻이고, `0x12`는 뒤에 토픽과 페이로드 18바이트가 이어진다는 뜻입니다. ASCII 파싱도, 문자열 오버헤드도 없습니다.

## QoS 세 단계: 무엇을 얻고 무엇을 내주는가

IoT 기기는 잡음 많은 무선 링크, 터널에서 끊기는 셀룰러망, 불안정한 위성 연결 위에서 동작합니다. 그래서 MQTT는 **QoS(Quality of Service)**라는 세 가지 전달 보장 수준을 둡니다.

QoS가 높을수록 좋다고 생각하기 쉽지만, 작성자는 각 단계가 대역폭·배터리 소모·전달 확실성 사이의 트레이드오프라고 강조합니다.

![The 3 Quality of Service (QoS) Guarantees and Handshakes](https://iili.io/nMf31dQ.png)

### QoS 0: 최대 한 번 (보내고 잊기)

```plaintext
[ Sender ] ─── PUBLISH ───> [ Receiver ]
```

가장 단순하고 빠릅니다. `PUBLISH` 패킷 하나만 보내고, 확인 응답을 요구하지 않습니다. 패킷 ID도 할당하지 않고 재전송 타이머도 없습니다. 패킷이 안테나를 떠나는 순간 연결이 끊기면 메시지는 영영 사라집니다.

**언제 쓰나:** 자주 들어오고 금방 의미가 없어지는 텔레메트리입니다. 기상 관측소가 2초마다 풍속을 보낸다면 한 번쯤 빠져도 2초 뒤 새 값이 옵니다. 굳이 확인 응답을 받느라 배터리를 쓸 이유가 없습니다.

### QoS 1: 최소 한 번 (확인 응답)

```plaintext
[ Sender ] ─── PUBLISH (PacketId: 10) ───> [ Receiver ]
[ Sender ] <─── PUBACK  (PacketId: 10) ─── [ Receiver ]
```

수신자가 최소 한 번은 메시지를 받도록 보장하지만, **중복 수신** 위험이 생깁니다.

1. 송신자가 `PUBLISH`에 16비트 `Packet Identifier`를 붙입니다.
2. 패킷을 로컬 메모리에 보관하고 확인 응답 타이머를 시작합니다.
3. 수신자는 패킷을 애플리케이션에 넘기고 같은 `PacketId`를 담은 `PUBACK`을 돌려줍니다.
4. 송신자는 `PUBACK`을 받으면 메모리에서 패킷을 지웁니다.

문제는 수신자가 `PUBLISH`를 받았는데 `PUBACK`이 돌아가기 직전에 네트워크가 끊길 때입니다. 송신자 타이머가 만료되면 `DUP` 플래그를 `1`로 켜고 다시 보내고, 수신자는 같은 메시지를 두 번 받게 됩니다.

그래서 QoS 1을 쓴다면 백엔드 컨슈머는 **반드시 멱등(idempotent)해야** 합니다. 같은 이벤트를 두 번 처리해도 DB가 꼬이거나 카드 결제가 두 번 나가서는 안 됩니다.

### QoS 2: 정확히 한 번 (4-way 핸드셰이크)

```plaintext
[ Sender ] ─── 1. PUBLISH (PacketId: 42) ───> [ Receiver ]
[ Sender ] <─── 2. PUBREC  (PacketId: 42) ─── [ Receiver ]
[ Sender ] ─── 3. PUBREL  (PacketId: 42) ───> [ Receiver ]
[ Sender ] <─── 4. PUBCOMP (PacketId: 42) ─── [ Receiver ]
```

손실도 중복도 없이 정확히 한 번 전달하는 방식으로, 내부는 두 단계 상태 머신입니다.

1. **PUBLISH:** 송신자가 `PacketId: 42`로 패킷을 보냅니다.
2. **PUBREC(Publish Received):** 수신자는 `PacketId: 42`를 내부 상태에 캐시하고 수신만 확인합니다. 아직 애플리케이션에는 넘기지 않습니다.
3. **PUBREL(Publish Release):** 송신자가 "받은 거 확인했으니 이제 처리해도 된다"고 알립니다.
4. **PUBCOMP(Publish Complete):** 수신자가 메시지를 처리하고 캐시에서 `PacketId`를 지운 뒤 `PUBCOMP`를 보냅니다. 양쪽 모두 트랜잭션을 마무리합니다.

중복은 완전히 사라지지만 **왕복이 두 번(패킷 4개)** 필요합니다.

**언제 쓰나:** 두 번 실행되면 큰일 나는 명령입니다. 전동 보안 게이트 열기, 의료 경보 울리기, 창고 재고 수량 차감 같은 경우입니다.

## 토픽 트리와 와일드카드 라우팅

MQTT는 고정된 큐 이름 대신, 슬래시로 구분한 계층형 문자열인 **토픽 트리**로 메시지를 라우팅합니다.

```plaintext
factory / building1 / line2 / motor4 / temperature
```

클라이언트는 이 가상 네임스페이스를 원하는 만큼 잘라서 구독할 수 있습니다.

![Topic Tree Hierarchy and Dynamic Wildcard Filtering](https://iili.io/nMf3WI1.png)

### 브로커는 트라이로 라우팅한다

기기 50만 대를 처리하는 브로커가 메시지마다 DB를 조회할 수는 없습니다. 브로커는 구독 정보를 메모리 안의 **트라이(Trie, 접두사 트리)**에 저장합니다.

슬래시(`/`)마다 자식 노드가 하나씩 생깁니다. `factory/building1/line2/motor4/temperature`로 패킷이 들어오면 브로커는 트라이 노드를 나노초 단위로 따라 내려가며 일치하는 클라이언트 소켓을 바로 찾습니다.

### 와일드카드 두 가지

**단일 레벨 와일드카드 `+`**는 토픽 트리의 **정확히 한 단계**와 일치합니다.

```plaintext
factory/+/line2/motor4/temperature
```

이 구독은 `factory/building1/line2/motor4/temperature`와 `factory/building2/line2/motor4/temperature`에 모두 일치합니다. 하지만 `factory/building1/subzone/line2/motor4/temperature`는 두 단계를 건너뛰므로 일치하지 않습니다.

**다중 레벨 와일드카드 `#`**는 **나머지 하위 단계 전부**와 일치하며, 반드시 토픽 필터 맨 끝에 와야 합니다.

```plaintext
factory/building1/#
```

이 구독 하나로 `building1` 안에서 나오는 센서 값, 모터 상태, 온도, 오류 코드, 진단 이벤트를 모두 받습니다.

### Retained 메시지: 상태를 잡아두는 걸쇠

일반 Pub/Sub에서는 대시보드가 오전 10시에 켜졌는데 스마트 온도계가 값이 바뀔 때만(9시 55분, 10시 30분) 발행한다면, 대시보드는 30분 동안 빈 화면을 보여줍니다.

`RETAIN=1` 플래그가 이 문제를 풉니다.

1. 브로커는 현재 구독자 모두에게 메시지를 전달합니다.
2. 그 메시지를 **메모리의 토픽 노드에 그대로 저장합니다.**
3. 이후 새 구독자가 그 토픽을 구독하면 **저장해둔 메시지를 즉시 보내** 초기 상태로 쓰게 합니다.

작성자의 표현대로, 흘러가 버리는 스트리밍 프로토콜이 즉석 상태 조회 엔진이 되는 셈입니다.

## 갑자기 죽은 기기 감지하기: KeepAlive와 Last Will

유선 환경에서는 클라이언트가 연결을 닫으면 OS가 TCP `FIN` 패킷을 보내고, 서버는 곧바로 연결 종료를 압니다.

IoT 기기는 이렇게 얌전하게 끊기는 일이 드뭅니다.

- 차량이 지하 콘크리트 주차장에 들어가 신호가 바로 끊깁니다.
- 현장 센서의 배터리가 완전히 방전됩니다.
- 공사 작업자가 실수로 이더넷 케이블을 끊습니다.

이런 상황에서는 **TCP FIN이 아예 전송되지 않습니다.** OS 커널 입장에서는 소켓이 여전히 열려 있으니, 별도로 확인하지 않으면 TCP keepalive 타이머가 소켓이 죽었다는 걸 알아채기까지 몇 시간이 걸릴 수도 있습니다.

MQTT는 **KeepAlive 하트비트**와 **Last Will and Testament(LWT)** 두 장치로 이 문제를 해결합니다.

![Last Will and Testament (LWT) & KeepAlive Heartbeat](https://iili.io/nMf3wBa.png)

### 1단계: 유언 등록

기기는 처음 접속할 때 `CONNECT` 패킷 안에 '유언'을 함께 담습니다.

- **Will Topic:** `devices/sensor-42/status`
- **Will Payload:** `{"state": "offline", "reason": "unexpected_disconnect"}`
- **Will QoS:** `1`
- **Will Retain:** `true`

브로커는 `CONNACK`으로 연결을 확인하고 유언을 조용히 메모리에 보관합니다. 기기가 정상인 동안에는 아무것도 하지 않습니다.

### 2단계: KeepAlive 핑

기기는 `KeepAlive` 간격을 초 단위로 지정합니다(예: `60`). 60초 동안 아무것도 발행하지 않았다면 2바이트짜리 `PINGREQ`(`0xC0 0x00`)를 보내고, 브로커는 바로 2바이트 `PINGRESP`(`0xD0 0x00`)로 답합니다.

이 2바이트 왕복으로 타이머를 초기화합니다. 셀룰러 데이터는 거의 쓰지 않으면서 통신사 NAT 방화벽의 포트도 열린 상태로 유지됩니다.

### 3단계: 돌연사 감지

브로커가 **KeepAlive의 1.5배**(이 예에서는 90초) 동안 기기에서 아무 패킷도 받지 못하면 다음과 같이 처리합니다.

1. 기기가 물리적으로 죽었다고 판단합니다.
2. TCP 소켓을 강제로 닫습니다.
3. **보관해둔 유언을 `devices/sensor-42/status`에 자동으로 발행합니다.**

이 토픽을 구독하는 대시보드, 모바일 앱, 백엔드 알림 시스템은 모두 `"state": "offline"` 알림을 곧바로 받습니다. 죽은 기기가 직접 알릴 필요 없이, 브로커가 미리 등록된 유언을 대신 집행하는 구조입니다.

기기가 의도적으로 정상 종료할 때는 `DISCONNECT`(`0xE0 0x00`)를 보냅니다. 그러면 브로커는 유언을 발행하지 않고 메모리에서 지웁니다.

## MQTT v5의 공유 구독: 클라우드 스케일링

오랫동안 표준은 MQTT v3.1.1이었습니다. 임베디드 하드웨어 쪽에서는 충분했지만, 클라우드 아키텍처에서는 큰 문제가 드러났습니다. **MQTT 토픽을 백엔드 마이크로서비스 클러스터에 어떻게 부하 분산할 것인가**입니다.

MQTT 3.1.1에서는 백엔드 워커 세 대가 `telemetry/#`를 구독하면 브로커가 모든 메시지를 **세 대 모두에게** 복사해 보냅니다. 커넥티드카 10만 대가 GPS 좌표를 보내면 워커마다 10만 개 스트림을 전부 처리해야 하니 수평 확장이 불가능합니다.

OASIS 위원회는 **MQTT 5.0**에서 **공유 구독(Shared Subscriptions)**을 도입해 이 문제를 풀었습니다.

![MQTT v5 Shared Subscriptions: Load Balancing IoT Streams](https://iili.io/nMf3k2R.png)

### 동작 방식

공유 구독은 **Kafka 컨슈머 그룹**과 같은 개념을 MQTT에 그대로 들여온 것입니다. 백엔드 서비스는 원래 토픽 대신 예약된 접두사를 붙여 구독합니다.

```plaintext
$share / <Group-Name> / <Topic-Filter>
```

예를 들면 다음과 같습니다.

```plaintext
$share/telemetry-processors/vehicles/+/gps
```

백엔드 인스턴스 세 대가 이 공유 구독으로 접속하면 이렇게 됩니다.

1. 브로커가 `$share/telemetry-processors` 접두사를 인식합니다.
2. 세 연결을 하나의 논리적 컨슈머 풀로 묶습니다.
3. 차량에서 GPS 패킷이 들어오면 라운드로빈 등으로 **그룹 내 워커 한 대에게만** 보냅니다.

워커 A가 바쁘면 2번 메시지는 B로, 3번은 C로 갑니다. 차량이 1,000대에서 100만 대로 늘어나면 백엔드 컨테이너를 열 대 더 띄우기만 하면 됩니다. 중간에 Kafka나 RabbitMQ 수집 계층을 따로 두지 않아도 브로커가 클러스터 전체에 부하를 나눠줍니다.

## 다른 프로토콜과 비교

작성자는 MQTT를 다른 주요 프로토콜과 이렇게 비교합니다.

| 항목 | MQTT | HTTP / REST | WebSockets | Apache Kafka |
| :--- | :--- | :--- | :--- | :--- |
| **기본 패러다임** | Pub/Sub 이벤트 브로커 | 요청 / 응답 | 양방향 스트림 | 분산 커밋 로그 |
| **헤더 오버헤드** | **최소 2바이트** | 500~2,000바이트 이상 | 2~14바이트 | 설정 / 배치 단위 |
| **전송 프로토콜** | TCP / TLS / WebSockets | TCP / TLS (HTTP/2, 3) | TCP / TLS | TCP / TLS |
| **기기 제약 대응** | 극한 (8비트 MCU) | 낮음 (HTTP 스택 필요) | 보통 | 없음 (대형 클라우드 서버) |
| **전달 보장** | QoS 0, 1, 2 | 애플리케이션 레벨 | 없음 (raw TCP) | 최소 한 번 / 트랜잭션 |
| **메시지 큐잉** | **없음 (휘발성)** | 없음 | 없음 | **영속 분산 로그** |
| **죽은 기기 감지** | **네이티브 LWT** | 헬스 체크만 | 소켓 하트비트 | 하트비트 타임아웃 |
| **적합한 용도** | 텔레메트리, 스마트 기기, 차량 IoT | CRUD API, 공개 웹 | 브라우저 UI 실시간 갱신 | 빅데이터 분석, 이벤트 재생 |

## 덜어냄으로 이긴 프로토콜

작성자는 MQTT를 "절제의 교과서"라고 부릅니다. JSON, GraphQL, 마이크로서비스로 계층을 계속 쌓아 올리는 업계 흐름과 반대로 갔기 때문에 성공했다는 겁니다. 근거로 세 가지를 듭니다.

1. **헤더를 바닥까지 줄였습니다.** 2바이트 헤더 덕분에 배터리와 대역폭을 프로토콜 형식에 낭비하지 않습니다.
2. **퍼블리셔와 컨슈머를 완전히 분리했습니다.** 기기는 누가 듣는지 모르기 때문에, 엣지 펌웨어를 건드리지 않고도 구독자를 한 명에서 백만 명까지 늘릴 수 있습니다.
3. **네트워크 장애를 기본 전제로 받아들였습니다.** QoS 핸드셰이크와 LWT 덕분에 가장 불안정한 물리 채널에서도 신뢰성을 확보합니다.

작성자는 IoT 아키텍처에서 가장 흔한 실수로 두 가지를 꼽습니다. MQTT를 단순한 HTTP 대체재로 취급하는 것, 그리고 MQTT가 알아서 영속 큐를 관리해줄 거라고 가정하는 것입니다. 바이너리 프레이밍, QoS 상태 머신, 브로커 라우팅 트리를 한 번 이해하고 나면 MQTT는 더 이상 정체 모를 블랙박스가 아닙니다.
