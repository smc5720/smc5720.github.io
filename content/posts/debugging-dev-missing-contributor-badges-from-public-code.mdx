## 개요

DEV(dev.to)에서 커밋을 4개 이상 머지한 기여자에게 주는 다중 커밋 뱃지가 사실상 아무에게도 지급되지 않고 있었습니다. DEV 팀 소속이 아닌 개발자 Dhruv Jani는 관리자 권한도, 운영 DB 접근 권한도, 내부 Slack도 없이 공개 저장소 `forem/forem` 코드만 읽고 원인을 찾아냈습니다. 수정 PR은 DEV 공동 창업자 Ben Halpern이 직접 머지했습니다.

글에서 더 오래 남는 대목은 따로 있습니다. 작성자가 회귀 테스트로 쓴 스펙이 **수정 전 코드에서도 그대로 통과했고**, 이 사실을 코드 리뷰에서 지적받았습니다.

![4x DEV Contributor Club badge](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/8fbepy9ufpk1x3tnksp9.png)
*4x DEV Contributor Club 뱃지: "Forem에 4개 이상의 커밋을 머지한 기여자에게 수여 — 기여해 주셔서 정말 감사합니다!"*

## 본문

### PR 4개를 머지했는데 뱃지는 하나뿐

작성자는 며칠 동안 `forem/forem`에 PR 4개를 머지했습니다.

- [#24003](https://github.com/forem/forem/pull/24003) — 문서: 깨진 Kamal 목차 앵커 수정, 누락된 가이드 색인 추가
- [#24056](https://github.com/forem/forem/pull/24056) — 접근성: 관리자 폼의 중복 `aria-describedby` 속성 제거
- [#24094](https://github.com/forem/forem/pull/24094) — 접근성: 크리에이터 설정의 끊어진 `aria-describedby` 참조 제거
- [#24095](https://github.com/forem/forem/pull/24095) — 뷰/Liquid: `user_subscription` 태그의 `src`에 따옴표 추가, 누락된 `alt` 추가

첫 PR이 머지되자 `1x`(`dev-contributor`) 뱃지는 바로 들어왔습니다. 그런데 네 번째 PR이 머지된 뒤에도 `4x-commit-club` 뱃지는 소식이 없었습니다.

작성자는 [`config/schedule.yml`](https://github.com/forem/forem/blob/main/config/schedule.yml#L77-L84)을 보고 `BadgeAchievements::BadgeAwardWorker`가 매시 20분(`cron: "20 * * * *"`)에 돈다는 걸 이미 알고 있었습니다. GitHub Contributors API(`/repos/forem/forem/contributors`)로 확인해 보니 자기 계정이 2페이지에 `contributions: 4`로 올라와 있었습니다. Forem은 [`Octokit.auto_paginate = true`](https://github.com/forem/forem/blob/main/config/initializers/octokit.rb#L1)로 설정돼 있어서 워커가 2페이지까지 읽는다는 것도 분명했습니다.

크론이 한 번, 두 번, 세 번 돌아도 뱃지는 들어오지 않았습니다.

![Mr. Bean waiting and checking his watch](https://media.giphy.com/media/tXL4FHPSnVJ0A/giphy.gif)
*매시 20분마다 프로필을 새로고침하는 작성자의 모습.*

작성자는 하루를 더 기다리는 대신 [`app/services/badges/award_contributor_from_github.rb`](https://github.com/forem/forem/blob/main/app/services/badges/award_contributor_from_github.rb)를 열었습니다.

### 코드에서 찾은 버그 세 가지

`main` 브랜치의 `Badges::AwardContributorFromGithub`는 뱃지 슬러그를 이렇게 하드코딩하고 있었습니다.

```ruby
BADGE_SLUGS = {
  "dev-contributor": 1,
  "4x-commit-club": 4,
  "8x-commit-club": 8,
  "16x-commit-club": 16,
  "32x-commit-club": 32
}.freeze
```

1x 뱃지를 주는 `award_single_commit_contributors`와 4x·8x·16x·32x를 담당하는 `award_multi_commit_contributors`를 나란히 놓고 보니 문제가 세 가지 보였습니다.

**1. 슬러그가 조용히 사라진다**

`BADGE_SLUGS`의 각 키는 `Badge.id_for_slug(slug)`로 ID를 찾습니다. 운영 DB의 `badges` 테이블에 같은 슬러그가 없으면 `nil`이 나오는데, 서비스는 결과에 `.compact`를 호출하고 그냥 넘어갔습니다. 에러도 로그도 남지 않고 해당 뱃지 등급만 통째로 빠졌습니다.

Forem은 `resources :badges, only: [:index]`만 열어 두기 때문에 `/badges/:slug` 같은 개별 조회 경로가 없습니다. 대신 공개된 [`dev.to/badges`](https://dev.to/badges) 목록에서 결정적인 단서가 나왔습니다.

> **`/badges`의 423번 뱃지:**
> - **제목:** `4x DEV Contributor Club`
> - **설명:** `4x-commit-club`

`4x-commit-club`은 설명 필드에 들어 있었습니다. `Badge#generate_slug`는 슬러그를 따로 지정하지 않으면 제목을 변환해 슬러그로 씁니다. 그래서 운영 DB의 실제 슬러그는 `4x-dev-contributor-club`이었고, 코드에 박힌 `"4x-commit-club"`과 맞지 않았던 것입니다.

![Charlie Day conspiracy board](https://media.giphy.com/media/l0IylOPCNkiqOgMyA/giphy.gif)
*DB 접근 없이 `Badge#generate_slug`와 `/badges` 페이지의 DOM ID를 이어 붙이는 중.*

**2. 감사 메시지가 빠진다**

1x 뱃지는 이렇게 지급했습니다.

```ruby
BadgeAchievement
  .where(user_id: i.user_id, badge_id: dev_contributor_badge_id)
  .first_or_create(rewarding_context_message_markdown: msg)
```

반면 다중 커밋 뱃지는 `.create`만 호출했습니다.

```ruby
BadgeAchievement.create(user_id: user_id, badge_id: slug_id)
```

그래서 뱃지가 생성되더라도 `rewarding_context_message_markdown`(`"Thank you so much for your contributions!"`)이 붙지 않았습니다. 커밋은 네 배인데 감사 인사는 없었던 셈입니다.

**3. 중복 방지 장치가 없다**

`create_badges_for_user`는 `.where(...).first_or_create(...)` 대신 `BadgeAchievement.create(...)`를 매시간 호출했습니다. 이미 받은 뱃지도 매번 다시 만들려 했고, ActiveRecord의 [`uniqueness` 검증](https://github.com/forem/forem/blob/main/app/models/badge_achievement.rb#L16)이 조용히 막아 주기만 바라는 구조였습니다. 뱃지에 `allow_multiple_awards: true`가 설정돼 있다면 상황은 더 나빠집니다. 매시간 중복 기록이 쌓이고, 그때마다 `after_create_commit :notify_recipient`와 [`send_email_notification`](https://github.com/forem/forem/blob/main/app/models/badge_achievement.rb#L22)이 실행돼 `yo@dev.to`에서 메일이 계속 날아갈 수 있었습니다.

### 이슈 등록과 PR #24113

작성자는 [이슈 #24114](https://github.com/forem/forem/issues/24114)에 뱃지 ID 423~426의 슬러그 불일치를 정리해 올리고, 서비스 코드를 고친 [PR #24113](https://github.com/forem/forem/pull/24113)을 함께 냈습니다.

1. 다중 커밋 뱃지에도 `rewarding_context_message_markdown: msg`를 붙였습니다.
2. `BadgeAchievement.create`를 `.where(...).first_or_create(...)`로 바꿨습니다.
3. 슬러그 조회를 GitHub 인증 공급자 확인 뒤로 미루고, 설정된 슬러그가 DB에 없으면 로그를 남기도록 했습니다.

### 코드 리뷰에서 나온 반전

Ben Halpern 계정으로 올라온 첫 리뷰는 Forem의 자동 리뷰 에이전트 **OpenHands**가 작성했습니다. 이 에이전트는 `badges` 테이블을 읽기 전용으로 조회해 작성자의 진단이 맞다고 확인했습니다.

> *"`BADGE_SLUGS`의 다섯 키로 `badges` 테이블을 읽기 전용 조회했습니다. 다섯 개 중 하나만 매칭됩니다. `Nx-commit-club` 슬러그 네 개는 일치하는 행이 없어서 `create_badges_for_user`가 건너뛰고, 현재 아무도 이 뱃지를 받을 수 없습니다. 이슈 작성자의 추측이 맞습니다."*

리뷰는 PR의 허점도 두 가지 짚었습니다.

**교훈 A: `warn` 로그는 소음이었다**

작성자는 처음에 누락된 슬러그마다 루프 안에서 `Rails.logger.warn`을 찍었습니다. 문제는 두 가지였습니다.

1. 운영 슬러그를 맞추기 전까지 DEV에서는 매시간 `warn`이 4줄씩 쌓입니다.
2. Forem은 DEV 말고도 여러 독립 커뮤니티를 운영합니다. 대부분의 자체 호스팅 Forem은 GitHub 인증을 켜 두면서도 DEV 전용 기여자 뱃지는 넣지 않습니다. 예상된 설정 때문에 매시간 `warn`이 쌓이면 `warn`은 아무도 보지 않는 배경 소음이 됩니다.

수정 커밋 [`5e36999`](https://github.com/forem/forem/commit/5e36999413bd4802f9020bf47ee3633c89b54c8d)에서는 누락된 슬러그를 모아 실행당 `Rails.logger.info` 한 줄만 남기도록 바꿨습니다.

**교훈 B: 회귀 테스트가 `main`에서도 통과했다**

중복 방지를 검증하려고 작성자는 `described_class.call`을 두 번 실행한 뒤 `4x-commit-club` 뱃지 기록이 여전히 1개인지 확인하는 스펙을 썼습니다. 테스트는 초록불이었습니다.

그런데 리뷰는 **이 테스트가 수정 전인 `origin/main`에서도 통과한다**고 지적했습니다.

![Surprised Pikachu](https://media.giphy.com/media/6nWhy3ulBL7GSCvKw6/giphy.gif)
*새로 쓴 회귀 테스트가 버그 수정 없이도 통과한다는 걸 알았을 때.*

원인은 `badge` 팩토리의 기본값 `allow_multiple_awards: false`였습니다. `main`에서 두 번째 `BadgeAchievement.create`는 `validates :badge_id, uniqueness: { scope: :user_id, if: :single_award_badge? }` 검증에 걸려 조용히 실패했고, 개수는 1로 유지됐습니다. 테스트가 확인한 건 `first_or_create`가 아니라 ActiveRecord의 uniqueness 검증이었습니다.

같은 커밋 `5e36999`에서 작성자는 뱃지를 `allow_multiple_awards: true`로 만들어 `main`의 `.create`가 실제로 중복을 넣는 조건을 갖췄습니다. 그리고 두 번째 실행에 대해 `expect { described_class.call }.not_to change(BadgeAchievement, :count)`로 검증하도록 스펙을 고쳤습니다.

### 작성자가 정리한 교훈 세 가지

1. **`main`에서 실패하는 걸 직접 보기 전까지는 회귀 테스트가 아니다.** 스펙이 초록불이 되면 `git stash`로 변경을 치우고 `main`에서 다시 돌려 봅니다. 그래도 통과한다면 회귀 테스트가 아니라 내 생각에 맞장구치는 테스트일 뿐입니다.
2. **로그 레벨은 운영자와의 약속이다.** `warn`은 누군가 조치해야 한다는 뜻입니다. 선택적으로 넣는 시드 데이터가 없는 건 `warn`이 아니라 `info`입니다.
3. **운영 환경을 디버깅하는 데 운영 권한이 꼭 필요하지는 않다.** 공개 소스 코드, 반증 가능한 가설, 단서를 끝까지 따라가는 호기심이면 충분합니다.
