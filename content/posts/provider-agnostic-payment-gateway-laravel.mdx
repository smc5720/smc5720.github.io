## 개요

스타트업처럼 제품을 빠르게 만드는 곳에서는 요구사항이 바뀌는 일이 흔합니다. 새 투자자나 고객이 들어오기도 하고, 이해관계자가 방향을 틀기도 합니다. 브라질 개발자 커뮤니티 He4rt의 Clinton Rocha는 그중 가장 자주 겪는 사례로 **결제 대행사(provider) 교체**를 꼽았습니다.

대행사를 하나만 쓸 때는 그 대행사에 맞춰 DB 테이블과 코드를 짜는 게 가장 빨라 보입니다. 하지만 몇 달 뒤 두 번째 대행사를 붙여야 할 때가 오면, 도메인 곳곳에 박힌 첫 번째 대행사의 용어 때문에 고생하게 됩니다. 저자는 이 문제를 **대행사에 종속되지 않는(provider-agnostic) 설계**로 풀자고 제안하고, Laravel(PHP) 예제 코드로 구현 방법을 보여 줍니다.

## 본문

### 왜 대행사를 바꾸게 되나

회사가 결제 대행사를 바꾸는 이유는 여러 가지입니다. 수수료가 더 낮은 곳이 생기기도 하고, 고객 지원 품질이나 서비스 성숙도, 신뢰성이 문제가 되기도 합니다. 저자는 대행사 대표가 회사와 아는 사이라는 이유로 바꾸는 경우도 있다고 덧붙였습니다. 이유야 어떻든, 교체는 언제든 일어날 수 있다는 얘기입니다.

### 대행사 용어가 도메인에 스며들면

마감이 빠듯한데 대행사가 하나뿐이라면, 그 대행사를 기준으로 모델링하고 연동하는 게 자연스럽습니다. 테스트도 통과하고 잘 돌아가죠. 문제는 새 대행사를 추가할 때 드러납니다. 테이블 구조와 도메인 코드가 모두 기존 대행사의 용어로 짜여 있어 서로 강하게 묶여(coupled) 있기 때문입니다. 저자는 이 상황이 해결하기는 귀찮지만, 미리 예상하고 막을 수 있는 문제라고 말합니다.

먼저 모델링이 대행사에 묶인 모습입니다.

![Image description](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/m5ez1dkhsu3dzqcrnrs1.png)

코드도 마찬가지입니다. Stripe와 Mercado Pago(중남미에서 많이 쓰는 결제 서비스)를 함께 쓰면, 결제 상태를 확인하거나 환불할 때마다 대행사별 분기가 반복됩니다.

```php
final class ReleaseProduct
{
    public function __invoke(Order $order): void
    {
        $isPaid = match ($order->provider) {
            'stripe' => $order->stripe_status === 'succeeded',
            'mercadopago' => $order->mercadopago_status === 'approved',
        };

        if (! $isPaid) {
            return;
        }

        $order->product->release();
    }
}

final class RefundOrder
{
    public function __invoke(Order $order): void
    {
        match ($order->provider) {
            'stripe' => $this->stripe->refund($order->stripe_payment_intent_id),
            'mercadopago' => $this->mercadoPago->refund($order->mercadopago_payment_id),
        };
    }
}
```

![Image description](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/y7v4lmg1oc372jixl9tn.png)

대행사가 하나 늘 때마다 `match` 분기와 대행사 전용 컬럼이 같이 늘어나는 구조입니다.

### "대행사가 바뀌면 어떻게 할 건데?"

저자는 모델링을 시작하기 전에 테크 리드에게 이런 질문을 받았다고 합니다. "대행사가 바뀌면 어떻게 할 건가요? X에서 Y로 옮기면 무엇이 영향을 받나요?" 처음에는 답을 몰랐고, 그때 배운 개념이 **agnostic** 설계였습니다.

> 컴퓨팅에서 어떤 장치나 소프트웨어가 데이터 전송 방식이나 형식과 상관없이 제 기능을 한다면 **agnostic(데이터 무관)**하다고 한다. 여러 형식이나 여러 출처의 데이터를 받아도 똑같이 처리할 수 있다는 뜻이다. — [Wikipedia](https://en.wikipedia.org/wiki/Agnostic_(data))

저자가 실제로 도움을 받은 사고방식은 이렇습니다. 같은 정보가 서로 다른 경로로 들어올 수 있다면, 모델링과 코드는 경로와 상관없이 똑같이 동작해야 합니다. 이 예제에서 정보는 "결제가 완료됐다"이고, 경로는 Stripe와 Mercado Pago입니다.

![Image description](https://dev-to-uploads.s3.us-east-2.amazonaws.com/uploads/articles/xsf5tnnav6uxl0fk36wh.png)

결제는 하나의 예일 뿐입니다. 인증(Auth0, Cognito, Firebase Auth), 이메일 발송(SES, SendGrid, Mailgun), 파일 저장(S3, Google Cloud Storage), SMS 발송(Twilio, Zenvia)에도 같은 생각을 적용할 수 있습니다. 저자는 Laravel을 쓴다면 이미 이 방식을 매일 쓰고 있다고 짚었습니다. `Mail`과 `Storage`는 뒤에 어떤 드라이버를 설정하든 똑같이 동작합니다.

### 도메인은 자기 언어로 말한다

대행사에 종속되지 않으려면 먼저 '도메인'이 무엇인지 알아야 합니다. DDD(Domain-Driven Design)에서 나온 용어로, 저자는 깊이 들어가지 않고 간단히 정리합니다. 도메인은 제품이 푸는 문제의 지식과 규칙이고, 코드에서는 그 규칙을 모아 둔 핵심 영역입니다. 예제에서는 '주문'이 도메인입니다.

대행사마다 쓰는 용어가 다릅니다. 결제 완료를 Stripe는 `succeeded`, Mercado Pago는 `approved`라고 부릅니다. 도메인은 팀이 정한 자기만의 이름, 예컨대 `paid`나 `canceled`를 쓰고, 대행사 용어는 도메인 안으로 들어오지 않게 합니다.

테이블도 도메인 용어만 담습니다. 대행사는 `provider`라는 값 하나로 남고, 대행사 쪽 ID는 범용 컬럼 `provider_reference`에 넣습니다.

```php
Schema::create('orders', function (Blueprint $table) {
    $table->id();
    $table->integer('amount_cents');
    $table->string('status');
    $table->string('provider');
    $table->string('provider_reference')->nullable();
    $table->timestamps();
});
```

```php
enum PaymentStatus: string
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Canceled = 'canceled';
}

enum PaymentProvider: string
{
    case Stripe = 'stripe';
    case MercadoPago = 'mercadopago';
}

final class Order extends Model
{
    protected function casts(): array
    {
        return [
            'status' => PaymentStatus::class,
            'provider' => PaymentProvider::class,
        ];
    }
}
```

### 대행사마다 번역기를 하나씩

다음은 대행사 API의 용어를 도메인 용어로 옮겨 주는 클래스입니다. 이 번역기가 [어댑터(adapter)](https://refactoring.guru/pt-br/design-patterns/adapter)이고, 모든 어댑터는 도메인이 정의한 같은 [계약(contract)](https://laravel.com/docs/contracts), 즉 포트(port)를 따릅니다. 이 번역 계층 전체를 [DDD](https://martinfowler.com/bliki/DomainDrivenDesign.html)에서는 부패 방지 계층(Anti-Corruption Layer)이라고 부릅니다.

```plaintext
                   도메인  ("paid", "canceled"로 말함)
  ┌─────────────────────────────────────────────────────┐
  │  ReleaseProduct      RefundOrder      HandleWebhook │
  └──────────────────────────┬──────────────────────────┘
                             │ 계약에만 의존
                 ┌───────────▼────────────┐
                 │ PaymentGatewayContract │  ← 포트
                 └───────────┬────────────┘
             ┌───────────────┴────────────────┐
  ┌──────────▼───────────┐       ┌────────────▼───────────┐
  │ StripeGateway        │       │ MercadoPagoGateway     │  ← 어댑터
  │ "succeeded" → paid   │       │ "approved"  → paid     │    (번역)
  └──────────┬───────────┘       └────────────┬───────────┘
             ▼                                ▼
         Stripe API                   Mercado Pago API
```

모든 대행사가 지켜야 할 계약은 다음과 같습니다.

```php
interface PaymentGatewayContract
{
    public function charge(Order $order): string;

    public function status(string $reference): PaymentStatus;

    public function refund(string $reference): void;
}
```

그다음 대행사마다 어댑터를 하나씩 만듭니다. 대행사 고유의 용어는 이 안에서만 쓰입니다.

```php
final class StripeGateway implements PaymentGatewayContract
{
    public function __construct(private StripeApi $api) {}

    public function charge(Order $order): string
    {
        return $this->api->createPaymentIntent($order->amount_cents)->id;
    }

    public function status(string $reference): PaymentStatus
    {
        return match ($this->api->getPaymentIntent($reference)->status) {
            'succeeded' => PaymentStatus::Paid,
            'canceled' => PaymentStatus::Canceled,
            default => PaymentStatus::Pending,
        };
    }

    public function refund(string $reference): void
    {
        $this->api->refundPaymentIntent($reference);
    }
}

final class MercadoPagoGateway implements PaymentGatewayContract
{
    public function __construct(private MercadoPagoApi $api) {}

    public function charge(Order $order): string
    {
        return $this->api->createPixPayment($order->amount_cents)->id;
    }

    public function status(string $reference): PaymentStatus
    {
        return match ($this->api->getPayment($reference)->status) {
            'approved' => PaymentStatus::Paid,
            'cancelled', 'rejected' => PaymentStatus::Canceled,
            default => PaymentStatus::Pending,
        };
    }

    public function refund(string $reference): void
    {
        $this->api->refundPayment($reference);
    }
}
```

### 하나로 묶기

어떤 대행사를 쓸지는 설정 파일에서 정합니다.

```php
// config/payments.php
return [
    'default' => env('PAYMENT_PROVIDER', 'stripe'),
];
```

리졸버는 대행사별로 어떤 어댑터를 쓸지 알고 있습니다.

```php
final class PaymentGatewayResolver
{
    public function for(PaymentProvider $provider): PaymentGatewayContract
    {
        return match ($provider) {
            PaymentProvider::Stripe => app(StripeGateway::class),
            PaymentProvider::MercadoPago => app(MercadoPagoGateway::class),
        };
    }
}
```

Laravel 컨테이너가 이 둘을 연결합니다. 계약을 요청하는 클래스에는 현재 설정된 대행사의 어댑터를 넘겨줍니다.

```php
final class AppServiceProvider extends ServiceProvider
{
    public function register(): void
    {
        $this->app->bind(
            PaymentGatewayContract::class,
            fn () => app(PaymentGatewayResolver::class)
                ->for(PaymentProvider::from(config('payments.default'))),
        );
    }
}
```

이제 처음에 봤던 클래스들은 뒤에 어떤 대행사가 있는지 몰라도 됩니다.

```php
final class ReleaseProduct
{
    public function __invoke(Order $order): void
    {
        if ($order->status !== PaymentStatus::Paid) {
            return;
        }

        $order->product->release();
    }
}

final class RefundOrder
{
    public function __construct(private PaymentGatewayContract $gateway) {}

    public function __invoke(Order $order): void
    {
        $this->gateway->refund($order->provider_reference);
    }
}
```

### 세 번째 대행사가 들어온다면

저자에 따르면 세 번째 대행사를 붙일 때 할 일은 세 가지뿐입니다. 어댑터를 새로 만들고, `PaymentProvider` enum에 케이스를 하나 추가하고, `PaymentGatewayResolver`에 한 줄을 넣으면 됩니다. `orders` 테이블과 `ReleaseProduct`, `RefundOrder`는 그대로 둡니다.
