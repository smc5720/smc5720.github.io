## 개요

보통 '게으른' 자동화 에이전트라고 하면 잡일을 대신 빨리 끝내 주는 도구를 떠올립니다. Khushighosh가 만든 **Let It Die**는 방향이 반대입니다. 그 일을 애초에 해야 하는지부터 묻습니다.

이 에이전트는 받은 메일마다 "무시하면 손해를 볼 가능성"을 점수로 매기고, 점수에 따라 메일을 세 갈래로 나눕니다. 하위 20%는 바로 버리지 않고 7일짜리 타이머에 걸어 둡니다. 그 사이 발신자가 다시 연락하면 중요 메일로 올리고, 아무 연락이 없으면 보관 처리합니다.

Hacktoberfest 오픈소스 AI 챌린지 3주차(주제: Slow and Steady) 출품작이며, 공개 데이터인 Enron 메일 1,981통으로 시험했을 때 398통(20%)을 타이머에 걸었고 그중 약 85%는 실제로 답장이 없던 메일이었습니다.

## 어떻게 동작하나

### 메일을 세 갈래로 나눈다

점수 순서에 따라 메일은 다음 중 한 곳으로 갑니다.

- **확인 필요 (상위 20%)**: 로컬에서 돌아가는 Gemma 모델이 두 줄 요약과 권장 조치를 써서 아침 다이제스트에 넣습니다.
- **낮은 우선순위 (중간 60%)**: 손대지 않고 다이제스트에 개수만 표시합니다.
- **Let it die (하위 20%)**: Temporal의 내구성 타이머(durable timer)에 걸어 둡니다. 7일 안에 발신자가 후속 메일을 보내면 승격하고, 없으면 보관합니다.

작성자는 핵심을 이렇게 표현합니다. 가장 빨리 끝나는 일은 시작조차 하지 않은 일이고, 단 어떤 일이 그런 일인지 가려낼 수만 있으면 된다는 것입니다.

시험용 메일로 돌린 실제 출력은 다음과 같습니다.

```plaintext
397 need you | 1186 low-priority | 398 parked on a timer (let it die)
In the 'need you' bucket, 46% were actually replied to (overall: 30%)

- john.henderson@enron.com | Wharton Tm #3 Presentation | he replied
  Summary: John reviewed the Wharton Tm #3 presentation and found it to be a good start.
```

타이머 데모에서는 Let it die 그룹에서 메일 8통을 무작위로 골랐습니다. 7통은 보관 처리됐고 7통 모두 실제로 답장이 필요 없는 메일이었습니다. 나머지 1통은 발신자가 다시 메일을 보내 승격됐습니다.

### 파이프라인 구성

```plaintext
emails -> TabPFN score -> triage -+- need you -> Gemma summary -> morning digest
                                  +- low priority -> counted only
                                  +- let it die -> Temporal timer (7 days)
                                                    +- follow-up signal -> escalate
                                                    +- timeout -> archive
```

- **TabPFN (Prior Labs)**: 메일 주인이 7일 안에 답장했는지를 예측합니다. 쓰는 특징값은 해당 메일이 도착하기 전에 알 수 있던 정보로만 만들었습니다. 발신자 이력, 수신자 구성, 수신 시각, 제목과 본문의 단서, 스레드 길이 등입니다. 별도 학습 과정이 필요 없습니다.
- **Gemma (Ollama로 gemma3:4b 로컬 실행)**: '확인 필요' 메일의 요약과 권장 조치를 작성합니다.
- **Temporal**: 타이머에 걸린 메일마다 워크플로를 하나씩 띄웁니다. 후속 메일 신호와 7일 타임아웃 중 먼저 오는 쪽을 기다렸다가 승격하거나 보관합니다. 데모에서는 Temporal의 시간 건너뛰기(time-skipping) 테스트 서버를 써서 일주일 대기를 몇 초 만에 끝냈습니다. 일부러 첫 보관 시도를 실패하게 만들자 Temporal이 전부 자동으로 재시도했고, 보관된 7통 모두 2번째 시도에서 처리됐다는 기록이 남았습니다.
- **Sentry**: 에이전트, 분류 단계, Gemma 호출 하나하나(모델명, 토큰 수, 전체 프롬프트와 응답), Temporal 단계까지 전체 실행을 추적합니다. 총 23초 중 약 22초가 로컬 Gemma 호출 다섯 번에 쓰였고, 각 호출은 작성자 본인 PC인 127.0.0.1로 가는 HTTP 요청이었습니다. 분류는 약 1밀리초, 메일 8통을 타이머에 거는 데는 약 1.3초가 걸렸습니다.

## 성능은 어느 정도인가

### 데이터 준비

작성자에게는 주고받은 메일이 양쪽 다 남아 있는 메일함이 없었습니다. 그래서 공개 Enron 코퍼스(CMU, 2015년 5월 배포판)에서 약 28,000통이 든 메일함 하나를 골랐습니다. 보낸편지함까지 들어 있어 답장 여부를 라벨로 만들 수 있기 때문입니다. 라벨 기준은 "메일 주인이 같은 스레드에서 7일 안에 답장했는가"입니다.

2001년 5월 이후로는 보낸 메일이 보관되지 않아 그 뒤 메일은 전부 답장이 없는 것처럼 보입니다. 그래서 기간을 1999년 11월부터 2001년 5월까지로 잘랐고, 쓸 수 있는 메일은 9,902통이 남았습니다. 시간순으로 앞쪽 80%(7,921통)를 학습에, 뒤쪽 20%(1,981통)를 시험에 썼습니다. 시험 데이터의 70.5%는 답장이 없던 메일입니다. 시간 기준으로 나눴으니 모델이 미래 정보를 볼 수 없습니다.

### 비교 결과

| 모델 | ROC AUC | 하위 10% 무시: 실제 무답장 비율 / 놓친 답장 메일 | 하위 20% 무시 |
|---|---|---|---|
| 발신자 답장률 규칙 | 0.579 | 68.2% / 10.8% | 73.7% / 17.8% |
| Gradient boosting | 0.662 | 92.4% / 2.6% | 88.4% / 7.9% |
| TabPFN | 0.687 | 92.9% / 2.4% | 84.6% / 10.4% |

작성자가 내린 해석은 이렇습니다.

- 두 모델 모두 발신자의 과거 답장률만 보는 규칙보다 확실히 낫습니다.
- TabPFN의 AUC가 0.024 높지만(부트스트랩 95% 신뢰구간 0.003~0.043), 하위 20% 구간에서는 gradient boosting이 앞섭니다. 작성자는 두 모델이 비슷한 수준이라고 봅니다.
- 실용적으로 보면, 메일 10통 중 1통꼴로 타이머에 걸어도 92~93%는 맞고, 실제 답장한 메일 중 놓치는 비율은 약 2.5%입니다.
- 시험 데이터에서 '확인 필요' 그룹의 답장률은 46%로 전체 평균 30%보다 높았고, Let it die 그룹은 약 15%였습니다. 작성자 표현대로 이 도구는 우선순위를 매겨 주는 도구이지, 정답을 아는 예언자가 아닙니다.

### 실제로 얼마나 덜어 주나

시험 데이터 1,981통 기준으로 에이전트는 398통(20%)을 메일 주인의 할 일에서 덜어 냈고, 그중 약 85%는 실제로 답장이 없던 메일이었습니다. 대가는 나머지 15%입니다. 약 60통은 실제로 답장했던 메일인데, 발신자가 다시 재촉하지 않으면 그대로 보관됐을 겁니다. 답장한 전체 메일의 약 10%에 해당합니다.

요약 하나에는 작성자의 노트북 기준 약 4초가 걸립니다. 다만 본인 메일함에 적용해 보지는 않았기 때문에, 몇 분을 아꼈는지는 정직하게 숫자로 말할 수 없다고 밝혔습니다.

### 파일이 전부 사라진 것처럼 보였다

Enron 메일 파일명은 `1.`, `10.`처럼 마침표로 끝납니다. Windows가 이 마침표를 조용히 떼어 버리는 바람에 Python은 메일함이 비어 있다고 판단했습니다. Windows의 확장 길이 경로 접두사(extended-length path prefix)로 바꾸고 나서야 해결됐습니다.

### 첫 시험 데이터에 답장이 하나도 없었다

모델 정확도가 98%로 나왔는데, 의미 없는 숫자였습니다. 월별 표를 뽑아 보니 2001년 6월부터 답장 수가 정확히 0이었습니다. 그 시점부터 아카이브에 보낸 메일이 없었기 때문입니다. 그래서 기간을 거기서 잘랐습니다.

### Gemma가 엉뚱한 메일을 요약했다

발신자가 맨 위에 한 줄을 쓰고 아래에 긴 전달 메일 묶음을 붙인 경우, 요약은 가장 오래된 전달 메일 내용을 설명하고 있었습니다. 캐시된 메일 원문과 요약을 나란히 놓고 읽다가 발견했습니다.

각 메일을 첫 번째 전달 메일 표시에서 잘라 내자 문제가 풀렸습니다. 수정 전후 버전을 각각 다섯 번씩 돌렸고(그중 마지막 두 번은 temperature 0, 고정 시드), 수정 전 버전은 매번 전달 메일을, 수정 후 버전은 매번 발신자의 답장을 요약했습니다. 해당 메일의 프롬프트도 649토큰에서 90토큰으로 줄었습니다.

## 한계

작성자는 한계도 구체적으로 적어 두었습니다.

- "7일 안에 답장했다"는 "조치가 필요했다"를 대신하는 근사치일 뿐이고, "발신자가 다시 메일을 보냈다"는 신호에도 잡음이 많습니다. 데모에서 승격된 메일 하나는 같은 제목을 반복해서 보내는 메일링 리스트에서 온 것이었습니다.
- 메일함 하나, 시간 기준 분할 한 번으로만 검증했습니다. 부트스트랩 구간은 메일을 서로 독립으로 가정하지만 실제로는 스레드와 발신자끼리 묶이는 경향이 있어, 구간이 실제보다 조금 좁게 나왔을 가능성이 큽니다.
- 타이머 데모는 메일 8통과 시뮬레이션 시계로 돌렸고, '보관'은 실제 메일을 옮기는 대신 로그 파일에 기록만 합니다.
- Gemma 출력은 매번 달라지고, 같은 프롬프트도 실행마다 지연 시간이 2배 정도 차이가 났습니다. 그래서 토큰 수는 전달 메일 수정 사례에만 인용했습니다. 이 수정도 메일 한 통 사례일 뿐 벤치마크가 아니며, 권장 조치 문구는 실행마다 바뀝니다.
- 첨부 파일 내용은 메일 텍스트에 들어가지 않아, 첨부 파일만 있는 메일의 권장 조치는 두루뭉술하게 나옵니다.

## 왜 오픈소스로 만들었나

작성자는 오픈 모델과 오픈소스 도구를 고른 이유를 네 가지로 정리했습니다.

- **메일을 읽는 모델이 내 PC에서 돈다.** Gemma는 Ollama로 로컬 실행되고, Sentry 추적 기록에서도 모든 모델 호출이 127.0.0.1로 향합니다. API 요금이 없고, 제3자가 메일 내용을 볼 일도 없습니다.
- **스케줄러를 직접 운영하지 않아도 된다.** Temporal의 오픈소스 도구 덕분에 재시작해도 살아남는 타이머와 불안정한 단계의 자동 재시도를 얻었습니다. cron 작업이나 직접 만든 큐가 필요 없습니다.
- **학습 과정이 없다.** TabPFN은 개인 메일함 정도의 작은 데이터에 학습 단계 없이 바로 맞춰집니다. 다만 작성자는 호스팅 API를 썼기 때문에 학습용 5,000행이 Prior Labs 서버로 전송됐다고 밝혔습니다. 공개 데이터인 Enron 메일이라 가능했던 선택이고, 개인 메일에 적용하려면 로컬 가중치를 쓰거나 이 점을 감수해야 합니다.
- **누구나 수치를 재현할 수 있다.** 데이터는 공개돼 있고 코드는 저장소에 있습니다.

호스팅 LLM과는 비교하지 않았기 때문에 요약 품질에서 오픈 모델이 낫다고 주장하지는 않는다고 덧붙였습니다. 이 프로젝트에서 오픈을 고른 이유는 프라이버시, 비용, 그리고 외부 서비스가 계속 살아 있어야 한다는 의존에서 벗어나는 것입니다.

## 코드

[GitHub 저장소 보기 →](https://github.com/Khushighosh/let-it-die)

MIT 라이선스이며, README에 Windows·Python 3.12 기준 실행 방법이 있습니다.

작성자는 챌린지의 TabPFN, Gemma, Temporal, Sentry Agent Tracing 부문에 출품했습니다. TabPFN은 규칙·gradient boosting과 비교한 답장 예측기로, Gemma는 실패와 수정 과정을 문서화한 로컬 요약기로, Temporal은 메일마다 하나씩 띄운 내구성 워크플로로, Sentry는 토큰 수·프롬프트·응답과 전달 메일 수정 전후를 담은 전체 실행 추적으로 냈습니다.
