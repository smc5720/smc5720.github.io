## 개요

인도의 인증기관(CA) eMudhra가 운영하던 중간 CA 인증서 8개의 개인 키를 **숫자를 하나씩 세어 보는 것만으로** 복구할 수 있었습니다. 슈퍼컴퓨터나 양자컴퓨터, 정교한 암호 공격은 전혀 필요하지 않았습니다.

겉으로 보면 평범한 인증서였습니다. 익숙한 CA 이름이 찍혀 있었고 신뢰된 루트까지 체인이 이어졌으며 브라우저 검증도 통과했습니다. 감사도 두 차례나 지나갔습니다. 그런데 P-384 타원곡선 키여야 할 개인 키 값이 256보다 작았고, 널리 알려진 사례 하나는 값이 그냥 **4**였습니다.

글쓴이는 이 사고를 암호 실패이면서 동시에 운영, 리뷰, 사고 대응이 모두 실패한 사례로 봅니다. eMudhra는 최종 근본 원인 분석(RCA)을 아직 진행하고 있다고 밝혔습니다. 그래서 원문은 확인된 사실과 공개 보도에 나온 추정 경로를 나눠서 설명합니다.

## 본문

### 사건 요약

- **2025년 4월 30일**: eMudhra의 키 생성 세리머니(key ceremony)에서 중간 CA 8개용 약한 개인 키가 만들어졌습니다.
- 정상적인 P-384 개인 키는 거대한 난수여야 하지만, 이번에 문제가 된 키 값은 256 미만이었습니다.
- 인증서에는 짝이 되는 공개 키가 그대로 들어 있습니다. 누구든 작은 값을 차례로 대입해 보면 1초도 안 돼 개인 키를 찾아낼 수 있었습니다.
- 약한 중간 인증서는 **약 18개월 동안** 공개적으로 신뢰받았습니다.
- **2026년 10월 17일**: 한 연구자가 Chrome Root Program에 이 문제를 제보했습니다. Chrome과 Firefox는 해당 인증서를 빠르게 차단했고, eMudhra는 중간 인증서를 폐기한 뒤 고객 마이그레이션 지원을 발표했습니다.

공개 전에 이 약한 키를 누군가 악용했다는 증거는 현재까지 없습니다. 다행스러운 일이지만, 그렇다고 작은 사고가 되지는 않습니다.

### 중간 CA는 무슨 일을 하나

브라우저 주소창의 자물쇠 아이콘 뒤에는 신뢰 체인이 있습니다.

```text
Trusted root CA
      ↓ signs
Intermediate CA
      ↓ signs
Website or code-signing certificate
      ↓
Browser, device, or application accepts the certificate
```

루트 CA는 신뢰의 기준점입니다. 브라우저와 운영체제가 루트 스토어에 보관하고, 루트는 웹사이트 인증서에 일일이 서명하지 않고 중간 CA에 서명합니다. 실제 발급 업무는 중간 CA가 맡습니다. 허용된 범위 안에서 웹사이트, 소프트웨어 배포자 등의 인증서에 서명합니다.

그래서 중간 CA 개인 키가 공격자 손에 들어가면 피해가 웹사이트 하나로 끝나지 않습니다. 수많은 웹사이트나 서명된 프로그램을 진짜처럼 보이게 만드는 도구를 통째로 넘겨주는 셈입니다.

### 키 값이 '4'라는 게 왜 치명적인가

타원곡선 키에서 공개 키는 개인 키로부터 다음과 같이 계산합니다.

```text
Q = d × G
```

- `d`: 개인 키
- `G`: 곡선마다 정해진 공개 기준점
- `Q`: 인증서에 들어가는 공개 키

정상적인 P-384 키라면 `d`는 대략 384비트 엔트로피를 가진 난수입니다. 공개 키 `Q`만 보고 `d`를 거꾸로 알아내기가 사실상 불가능하다는 점이 타원곡선 암호의 핵심입니다. 단, 개인 키가 충분히 크고 무작위여야 한다는 전제가 붙습니다.

`d`가 256보다 작으면 어려운 수학 문제를 풀 필요가 없습니다.

```text
1 × G
2 × G
3 × G
4 × G
...
255 × G
```

이렇게 계산한 값을 인증서의 공개 키와 비교하다가 일치하는 순간 개인 키가 드러납니다. 알고리즘 자체가 약해진 게 아닙니다. 키 생성 과정에서 너무 작은 값이 들어가는 바람에 알고리즘이 보안을 제공할 여지가 처음부터 없었습니다.

### 무엇이 잘못됐나: 겹겹이 쌓인 실패

eMudhra의 성명과 공개된 사고 논의를 종합하면, 실수 한 번이 아니라 여러 단계의 실패가 겹쳤습니다.

1. 세리머니의 원래 목표는 여러 중간 CA용 RSA-4096 키 쌍과 P-384 키 쌍을 제대로 생성하는 것이었습니다.
2. 절차에서 벗어난 작업으로 HSM 키 처리용 wrap-and-unwrap 테스트가 추가됐습니다.
3. 세리머니 스크립트의 결함 때문에 원래 키와 별도로 약한 EC 키 세트가 하나 더 생성됐습니다.
4. 약한 키 세트와 정상 키 세트의 라벨이 비슷했습니다.
5. 인증서 서명 요청(CSR)을 만들 때 잘못된 키 객체를 골랐습니다.
6. 그 결과 약한 공개 키가 중간 CA 인증서에 서명됐고, 호환성을 위해 교차 서명(cross-sign)까지 받았습니다.
7. 정상 키는 HSM에 그대로 남아 있었지만, 공개된 인증서와는 연결되지 않았습니다.

정확한 근본 원인은 아직 확정되지 않았습니다. 다만 큰 흐름은 이미 드러났습니다. **생성 결함이 나쁜 키를 만들었고, 선택과 검증 단계의 실패가 그 키를 세상에 내보냈습니다.** 어느 한쪽에서만 잡았어도 브라우저 신뢰 문제로 커지지는 않았을 겁니다.

### 모든 걸 멈췄어야 했던 경고

원문이 가장 불편한 대목으로 꼽는 부분은 최초의 스크립트 실수가 아니라 몇 주 뒤의 대응입니다.

2025년 5월 무렵 인증서 폐기 목록(CRL)의 서명 검증이 실패하기 시작했습니다. CRL은 더 이상 신뢰하면 안 되는 인증서 목록에 CA가 서명한 것입니다. CRL에 서명한 개인 키가 발급 CA 인증서의 공개 키와 맞아야 검증이 통과합니다. 검증이 실패했다면 시스템은 이렇게 말하고 있던 셈입니다.

```text
The private key signing this CRL does not match
the public key advertised in this CA certificate.
```

CA 입장에서는 그 자체로 사고입니다. 그런데 공개 보도에 따르면 CRL 서명자 설정을 약한 키 세트 쪽으로 바꿔서 서명이 통과하게 만들었습니다. 증상은 사라졌지만 왜 키 세트가 두 개 있는지, 왜 공개된 인증서가 예상한 HSM 서명 키와 맞지 않는지는 묻지 않았습니다. 경보가 왜 울렸는지 알아내지 않고 경보만 끈 것입니다.

### 놓쳐버린 RCA

"잘못된 키가 설정돼 있었다"는 한 줄로는 RCA가 되지 않습니다. 사람이나 설정 하나에서 멈추지 말고, 실제로 무너진 통제 장치가 나올 때까지 계속 물어야 합니다.

얕은 분석은 이런 모습입니다.

| 단계 | 얕은 답 |
| --- | --- |
| 증상 | CRL 서명이 검증되지 않음 |
| 직접 원인 | 서명자가 잘못된 키를 쓰고 있음 |
| 조치 | 다른 키를 쓰도록 변경 |
| 상태 | 종료 |

이 분석은 여분의 키가 존재한다는 사실을 당연하게 받아들입니다. 제대로 하려면 이렇게 물어야 합니다.

| 질문 | 조사로 밝혀야 할 것 |
| --- | --- |
| CRL 서명은 왜 실패했나? | 서명자 개인 키가 중간 인증서의 공개 키와 맞지 않았다. |
| 왜 맞지 않았나? | CSR이 의도한 HSM 서명 키가 아닌 다른 키 쌍을 사용했다. |
| 왜 키 쌍이 두 개였나? | wrap-and-unwrap 테스트 중에 키가 추가로 생성됐다. |
| 왜 잘못된 키를 골랐나? | 라벨과 선택 절차만으로는 의도한 키를 명확히 구분할 수 없었다. |
| 발급 전에 불일치를 왜 못 잡았나? | 각 CSR이 의도한 HSM 키와 일치하는지 세리머니 이후 독립적으로 대조하는 절차가 없었다. |

두 번째 질문에서 이미 사고를 발견할 수 있었습니다. CSR의 공개 키 지문과 HSM 객체의 공개 키 지문을 비교하거나, 키 속성을 들여다보거나, EC 공개 포인트에 간단한 점검만 돌렸어도 됐습니다. 그랬다면 생태계 전체를 흔든 사고가 내부 재세리머니로 끝났을 겁니다.

### 감사 두 번은 왜 못 잡았나

"감사를 두 번 받았는데도 못 잡았다"는 말을 들으면 감사가 쓸모없다고 결론 내리기 쉽습니다. 원문은 그게 교훈이 아니라고 말합니다.

감사는 보통 문서화된 통제가 존재하고 지켜지는지를 확인합니다. 세리머니를 참관하고 기록을 표본으로 살펴보고 승인과 절차를 검토합니다. 생성된 암호 키 하나하나의 보안 속성을 다시 계산해 보는 일까지는 대개 하지 않습니다.

담당자가 모두 참석하고, 서식과 HSM이 제대로 갖춰지고, 체크리스트에 서명까지 끝나도 치명적으로 약한 키는 얼마든지 공개될 수 있습니다. 절차를 지켰다는 증거와 암호학적 검증은 다른 문제입니다. CA라면 키 자체를 검증해야 합니다.

- CSR의 공개 키가 의도한 HSM 키와 지문 기준으로 일치하는가?
- 중간 CA마다 승인된 키 쌍이 정확히 하나씩만 있는가?
- EC 공개 키가 작은 스칼라 값 점검(small-scalar sanity check)을 통과하는가?
- 생성된 키 객체가 전부 세리머니 계획과 맞아떨어지는가?
- 세리머니 스크립트가 스스로 검증하는 대신, 독립된 도구로 결과를 확인했는가?

루트가 브라우저 스토어에서 빠지는 비용에 비하면 모두 값싼 점검입니다.

### 폐기만으로는 부족했던 이유

eMudhra는 해당 중간 인증서를 폐기했습니다. 꼭 필요한 조치였지만 그것만으로는 충분하지 않았습니다.

폐기가 효과를 내려면 클라이언트가 폐기 정보를 받아 와서 실제로 적용해야 합니다. 꼬박꼬박 확인하는 클라이언트도 있지만, 네트워크 오류가 나면 그냥 통과시키는(soft-fail) 클라이언트도 있고 아예 확인하지 않는 클라이언트도 있습니다. Chrome과 Firefox는 모든 클라이언트가 CRL을 내려받기를 기다리지 않고 긴급 불신 정보를 직접 배포할 수 있습니다. 제보 직후 빠르게 차단할 수 있었던 이유입니다.

문제는 교차 서명이었습니다. 해당 중간 인증서는 Sectigo의 AAA Certificate Services 아래에도 교차 서명된 사본이 있었습니다. 최신 eMudhra 루트가 없는 구형 기기도 교차 서명한 루트는 신뢰할 수 있도록 하려는, 나름 합리적인 호환성 조치였습니다. 하지만 이번에는 위험을 키우는 요인이 됐습니다.

```text
Same weak intermediate key
        ↙                    ↘
eMudhra trust path      Sectigo cross-signed path
```

eMudhra 경로만 막아서는 다른 경로로 이어진 체인을 받아들이는 클라이언트를 막을 수 없습니다. 브라우저들이 교차 서명 경로까지 따로 처리해야 했던 이유입니다.

### 브라우저 밖도 봐야 한다

브라우저 차단은 눈에 잘 띄고 빠릅니다. 백엔드 클라이언트는 조용합니다. CLI 도구, 내부 서비스, 자체 모바일 앱, 임베디드 기기, Java 런타임, 사설 트러스트 스토어, 인증서를 고정(pinning)했거나 오래된 CA 번들을 쓰는 애플리케이션은 같은 시점에 같은 긴급 보호를 받지 못할 수 있습니다. Certificate Transparency나 폐기 확인을 처리하는 방식도 제각각입니다.

원문은 엔지니어링 팀에 한 가지를 분명히 당부합니다.

> 신뢰 체인 마이그레이션 때문에 연결이 실패했다고 해서 인증서 검증을 끄지 마세요.

그렇게 하면 호환성 문제가 보안 우회로 바뀝니다. CA 체인을 더 이상 신뢰하지 않아 서비스가 깨졌다면 인증서, 트러스트 스토어, 클라이언트 라이브러리, 설정을 제대로 고쳐야 합니다. 임시로 넣은 "verify false" 같은 설정이 다음 사고의 씨앗이 됩니다.

### CA가 바꿔야 할 것

원문이 제시하는 통제는 특별하지 않습니다.

1. **세리머니 결과를 대조한다.** 세리머니가 끝나면 HSM 키 객체를 모두 나열하고 승인된 계획과 비교합니다. CA 하나당 예상한 키 쌍이 정확히 하나여야 하고, 예상하지 못한 키 객체가 있으면 작업을 멈춥니다.
2. **라벨이 아니라 지문으로 키를 고른다.** 이름은 비슷할 수 있고 운영자는 잘못 읽을 수 있습니다. 세리머니 기록에 묶인 SHA-256 지문은 헷갈리기 훨씬 어렵습니다.
3. **공개 키를 독립적으로 검증한다.** 별도의 도구와 별도의 검토자가 CSR 공개 키와 승인된 HSM 객체가 일치하는지 확인합니다. 세리머니 스크립트가 자기 결과를 스스로 보증하게 둬서는 안 됩니다.
4. **서명 전에 키 품질을 점검한다.** EC 키는 작은 스칼라 값인지 확인하고, RSA 키는 약하거나 공유된 인수가 없는지 확인합니다. 고객의 CSR을 점검하는 만큼은 자기 서명 키도 꼼꼼히 봐야 합니다.
5. **설명되지 않는 암호 오류는 사고로 다룬다.** CA 키가 얽힌 서명 검증 실패라면 근본 원인을 문서화하고 증거를 보존하고 독립 검토를 거친 뒤에 종료해야 합니다. "키를 바꾸니까 된다"는 조사의 시작이지 끝이 아닙니다.
6. **세리머니 절차 변경을 보안 변경으로 다룬다.** wrap-and-unwrap 테스트는 작은 변경처럼 들리지만 비밀 키 처리를 건드립니다. 별도 리뷰, 비운영 HSM에서의 사전 리허설, 변경된 스크립트와 독립된 결과 점검이 필요합니다.
7. **교차 서명된 중간 인증서를 다시 점검한다.** 교차 서명은 누가 그 키를 신뢰하는지를 바꿉니다. 신뢰 경로가 새로 생길 때마다 같은 키 품질 검증을 거치고, "문제가 생기면 이 키를 모든 곳에서 어떻게 막을 것인가"에 답할 수 있어야 합니다.

### CA가 아닌 팀이 가져갈 교훈

대부분의 팀은 CA를 운영하지 않지만, 교훈은 그대로 적용됩니다.

- **보안 점검 실패는 신호다.** 무결성 검사가 실패하면 원인을 이해하기 전까지 검증 경로를 바꿔서 통과시키지 마세요. 비싼 사고는 누군가 귀찮다고 넘긴 경고에서 시작하는 경우가 많습니다.
- **자동화에는 독립된 검증이 필요하다.** 자동화는 잘못된 결정도 아주 빠르게 반복합니다. 자격 증명, 인증서, 서명 키, 백업, 접근 제어를 만드는 자동화라면 별도의 도구나 컨트롤 플레인에서 결과를 확인하세요.
- **신뢰 의존성을 파악해 둔다.** 외부로 나가는 HTTPS 클라이언트는 모두 인증서 검증에 의존합니다. 사설 트러스트 스토어, 고정 인증서, 오래된 Java 번들, 임베디드 펌웨어, 특이한 프록시 설정을 쓰는 애플리케이션 목록을 비상 상황이 닥치기 전에 만들어 두세요.
- **교체 속도도 보안 통제다.** 키와 인증서를 빠르게 교체할 수 있느냐에 따라 신뢰 사고가 몇 시간으로 끝날지, 몇 달을 끌지가 갈립니다.

### 아직 밝혀지지 않은 것

원문은 1차 자료가 나올 때까지 다음 질문들을 열어 두자고 말합니다.

- eMudhra의 최종 근본 원인 분석과 외부 전문가 검토 결과
- 세리머니 코드의 정확한 결함과 그 결함을 통과시킨 통제
- 2025년 5월 CRL 서명 실패를 내부에서 어떻게 처리했는지 전체 경위
- 브라우저 보호 범위 밖에서 해당 키로 만든 체인을 받아들인 클라이언트가 있었는지
- 브라우저와 운영체제 트러스트 스토어 조치의 최종 범위

현재 공개 보도로는 공개 이전의 악용 사례가 알려지지 않았습니다. Chrome도 차단 전까지 영향받은 TLS 중간 인증서 6개로 발급된 TLS 인증서가 로그에 기록된 적이 없다고 밝혔습니다. 덕분에 알려진 피해 범위는 좁아졌지만, 통제가 무너진 데서 배워야 할 교훈은 그대로입니다.
