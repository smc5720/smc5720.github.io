## 개요

Rails World 2026 무대에서 DHH가 [코드를 손으로 치는 일은 이제 "펜을 내려놓았다"(pencils down)고 말했습니다](https://dev.to/techaiwire/rails-world-2026-dhh-says-hand-written-code-is-obsolete-pdj). 37signals가 요즘 Rust 코드를 얼마나 많이 내보내고 있는지도 털어놨죠. Rust를 읽는 건 "눈에 산을 붓는 것 같다"고 농담하면서도, AI 에이전트가 borrow checker를 맡아주니 30배에서 100배까지 빨라지고 바이너리는 아주 작아지며 시작 시간은 1밀리초도 안 걸린다고 극찬했습니다.

인터넷 한쪽에서는 이 발표를 Rails의 패배 선언처럼 받아들였습니다. Rails를 만든 사람조차 Rust를 꺼내 드는데, Ruby와 Rails는 어떻게 되느냐는 반응이었죠.

DEV 창업자 Ben Halpern은 정반대로 봅니다. DEV를 구동하는 Rails 모놀리스 [Forem](https://github.com/forem/forem)도 지난 한 달 동안 내부 Ruby 모듈 수십 개를 Rust로 바꿔왔습니다. 그런데 이 과정을 운영 환경에서 지켜보면서 오히려 Rails를 더 높이 평가하게 됐다고 말합니다. **Rails 코드베이스에 Rust를 이렇게 쉽게 넣을 수 있다는 것 자체가 결함이 아니라 장점이라는 겁니다.**

## 본문

### 마이크로서비스로 쪼개지 않아도 된다

예전에는 동적 웹 프레임워크에 넘기 힘든 벽이 하나 있었습니다. Ruby 덕분에 개발자들은 즐겁게 일하며 제품-시장 적합성까지는 빠르게 도달했습니다. 그런데 문자열 파싱이나 피드 점수 계산, 직렬화 같은 경로가 가비지 컬렉터를 짓누르기 시작하면, 누군가 Go나 Rust로 마이크로서비스를 따로 떼어내자고 나섰습니다. 하나였던 애플리케이션이 배포 두 개로 갈라지고, 네트워크 홉이 생기고, 인증 로직이 중복되고, 운영 부담이 영원히 따라붙었습니다.

Halpern은 이 벽이 이제 사용성 면에서나 아키텍처 면에서나 거의 사라졌다고 봅니다.

Forem에는 코드베이스를 상대로 쉬지 않고 돌아가는 자율 워크플로가 여럿 있습니다. 그중 하나인 `rust-loop`는 CPU를 많이 쓰거나 메모리 할당이 잦은 Ruby 핫 패스를 찾아 프로세스 내부 Rust 확장(`gems/forem_native`)으로 옮깁니다. 연결에는 `magnus`와 `rb-sys`를 씁니다. 그 결과는 앞서 쓴 글 [Our Looping Factory Cut DEV Page Load Time by 75% and Counting](https://dev.to/dailycontext/our-looping-factory-cut-dev-page-load-time-by-75-and-counting-1hnf)에 정리돼 있습니다.

### 무엇을 Rust로 옮겼나

`gems/forem_native`는 두 층으로 나뉩니다. 하나는 Ruby 의존성이 전혀 없는 순수 Rust 크레이트 `forem_core`이고, 다른 하나는 함수당 15줄 남짓한 `magnus` 래퍼입니다. 래퍼는 Ruby 문자열 버퍼를 직렬화나 메모리 복사 없이 그대로 빌려 씁니다. `rust-loop`는 다른 유지보수 루프 8개와 함께 컨트롤 패널([Ask More of Your UI](https://dev.to/dailycontext/ask-more-of-your-ui-2nf7) 참고)에서 모니터링되며, 지금까지 옮긴 모듈은 다음과 같습니다.

- 마크다운 전처리, 프론트매터 정규화, 읽기 시간 계산용 토큰화: 약 54배 빨라졌고 Ruby 힙 할당은 0이 됐습니다.
- 홈 피드 랭킹과 동적 `pgvector` SQL 표현식 조립: 약 20배 빨라졌고 Ruby 객체 할당은 97% 줄었습니다.
- HTML 정제(sanitization), 인라인 SVG 아이콘 렌더링, `@username` 멘션 파싱, URL 정규화, Public Suffix 기반 서브도메인 라우팅, 상수 시간 CSRF/JWT 검증, 에이전트 대화 기록에 대한 51개 패턴 비밀값 제거
- 순수 Ruby 의존성인 `gemoji`, `emoji_regex`, `wcag_color_contrast`는 `Gemfile`에서 아예 지웠습니다.

그래도 Forem을 클론하는 개발자는 `bin/dev`를 실행하려고 `cargo`를 설치할 필요가 없습니다. 미리 빌드한 300KB 남짓한 플랫폼별 바이너리가 macOS와 Linux에서 1밀리초 안에 로드됩니다. `Containerfile`은 멀티 스테이지 빌드로 공유 라이브러리를 컴파일하고 심볼을 제거하기 때문에, 프로덕션 이미지에는 Rust 툴체인이 하나도 남지 않습니다. 옮긴 함수는 모두 RSpec 차등 테스트로 검증합니다. 무작위 입력 1,000개 이상을 기존 Ruby 구현과 비교하는 방식입니다.

### Rails는 '다년생 화단'이다

Halpern은 [Design for Churn](https://dev.to/dailycontext/design-for-churn-5c6h)에서 AI 시대의 코드베이스를 정적인 건물보다는 정원에 비유했습니다. 구현 코드를 다시 쓰는 비용이 싸지면 진짜 투자는 다년생 화단에 들어갑니다. 스키마, 라우팅, 경계, 계약처럼 그대로 버티는 구조 말이죠. 그 안에 심은 한해살이 식물, 곧 구현은 계속 바뀝니다. [Jev 같은 System One 모델을 AI 스택에 들일 때](https://dev.to/dailycontext/you-should-know-about-system-one-models-3a9a)도 같은 원칙을 썼습니다. 정책과 도메인 구조는 Ruby로 깔끔하게 유지하고, 그 아래에 특화된 엔진을 갈아 끼우는 겁니다.

그가 보기에 Rails가 바로 그 다년생 화단입니다. [@techie_raj](https://dev.to/techie_raj)가 [Your Rails App Is Already AI-Ready. You Just Don't Know It.](https://dev.to/techie_raj/your-rails-app-is-already-ai-ready-you-just-dont-know-it-1jc4)에서 짚었듯이, `config/routes.rb`, `app/services/`, 선언적인 Active Record 스코프, 스스로를 설명하는 백그라운드 잡 같은 20년 묵은 관례 덕분에 Rails 코드는 읽기 쉽습니다. 신규 입사자도, 코딩 에이전트도 어렵지 않게 길을 찾습니다. [@ttebify](https://dev.to/ttebify)는 [Rust is amazing, as long as I'm not the one writing it](https://dev.to/ttebify/rust-is-amazing-as-long-as-im-not-the-one-writing-it-1k9f)에서 엄격한 컴파일러가 저수준 연산을 다루는 에이전트에게 빡빡하고 봐주지 않는 피드백 루프가 돼준다고 했습니다.

Rails가 주는 상위 수준의 일관성에 하드웨어에 가까운 Rust의 성능을 짝짓는다고 해서 Rails를 버리는 건 아니라고 Halpern은 강조합니다. 시스템 전체는 Rails가 깔끔하게 조율하고, 네이티브 속도가 필요한 지점에서는 비켜준다는 거죠. Rails가 원래 가장 잘하던 일입니다.

### 다들 하던 우회책을 정식 기능으로: `bin/rails query`

Halpern은 Rails가 오래 살아남는 이유를 보여주는 예로 Rails 8.2에 들어가는 새 기능을 꼽습니다. `rails-query-command`로 Rails 7.2, 8.0, 8.1에도 백포트됐습니다.

[관련 게시물 보기 →](https://x.com/jchibbard/status/2120569126150127666)

AI 코딩 에이전트에게 실제 일을 맡기는 팀은 결국 같은 벽에 부딪힙니다. 정적 소스 파일만 읽는 에이전트는 프로덕션 병목을 엉뚱하게 짚습니다. 그렇다고 자율 에이전트에게 실데이터에 붙은 `rails console`이나 `rails runner`를 제한 없이 내줄 수도 없죠. Halpern은 [AI Engineering Has Entered Its Audit Era](https://dev.to/dailycontext/ai-engineering-has-entered-its-audit-era-56fl)에서 이제는 에이전트 권한 범위를 정하고 결과물을 증명하는 일이 진짜 엔지니어링이 됐다고 썼습니다. 쓰기 쪽에서 같은 주제를 다룬 글로는 [@oleksandr_sainchuk](https://dev.to/oleksandr_sainchuk)의 [How we keep AI agent actions under server side control in rails](https://dev.to/oleksandr_sainchuk/how-we-keep-ai-agent-actions-under-server-side-control-in-rails-387e)가 있습니다.

Forem이 응답 시간을 70ms에서 16ms로 줄이는 과정에서도 직접 만든 우회책이 필요했습니다. 프라이버시 가드를 씌운 읽기 전용 Postgres 게이트웨이 `forem-db-query`입니다. 성능 루프는 코드를 한 줄 고치기 전에 이 게이트웨이로 실제 쿼리 플랜, 순차 스캔, 행 분포를 안전하게 확인했습니다. 다른 팀들도 읽기 전용 래퍼나 MCP 도구, 커스텀 rake 태스크를 조용히 만들어 같은 문제를 풀어왔습니다.

Halpern은 이미 우회책이 있더라도 상관없다고 말합니다. **직관적이고 꼭 필요한 것을 정식 기능으로 만들어 길게 보면 이득이 되게 하는 것, Rails는 바로 그러려고 존재한다고요.**

`bin/rails query`가 생태계 전체의 표준 명령이 되면 팀마다 만든 스크립트 스무 개가 관례 하나로 합쳐집니다. 이 명령은 계약상 읽기 전용이고, 구조화된 JSON을 출력하며, `schema`, `models`, `explain`을 기본으로 갖췄습니다. 개발자든, 운영 런북이든, 코딩 에이전트든 Rails 앱에 데이터에 관한 질문을 안전하게 던지는 법을 바로 알게 됩니다.

### 시대에 맞춰 일어서는 프레임워크

Halpern은 프레임워크가 쇠퇴하는 건 자기 경계를 순수성 시험처럼 다룰 때라고 봅니다. 모든 문제를 한 언어로 풀어야 한다고 고집하거나, 요즘 소프트웨어가 실제로 어떻게 만들어지는지 외면할 때죠.

그는 Rails가 지금까지 살아남아 여전히 앞서가는 이유가 Ruby 문법에 있지 않다고 말합니다. 핵심은 **안목과 통합 능력(taste and integration)** 입니다. 개발자가 제품을 내보내려면 실제로 필요한 지저분하고 실용적인 것들이 있습니다. 마이그레이션, 백그라운드 잡, 무중단 Kamal 배포부터 손쉬운 네이티브 Rust 확장, 에이전트가 안전하게 쓸 수 있는 데이터베이스 조회까지요. Rails는 이런 것들을 모아 지나고 보면 당연해 보이는 기본값으로 만들어왔습니다.

Forem은 DEV를 빠르게 만들 수 있는 곳이라면 앞으로도 핫 연산 루프를 Rust로 바꿔 나갈 계획입니다. 그리고 그 작업을 계속 Rails 모놀리스 안에서 기꺼이 하겠다고 했습니다. Halpern은 이 말로 글을 맺습니다. "Long live Rails, and Happy Coding ❤️"
